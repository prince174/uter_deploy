# Экспериментальный этап фиксации Pod Redis

`scripts/kubernetes_fence_finalizer.py` — отдельный исполняемый Python-адаптер,
не подключённый к установщику, обновлению или защитному барьеру. Он **не изолирует
Redis**, не останавливает Pod, не проводит резервирование и не разрешает переход
версий. Пользовательской команды обновления для него нет.

Перед использованием вызывающий код обязан удерживать исключительный lock
установки и достоверно выбрать конкретные Kubernetes context, namespace и Pod.
Адаптер сверяет UID, resourceVersion, имя и namespace Pod, текущий контейнер Redis,
его ID и хеш спецификации. Он не доказывает принадлежность Pod подписанному выпуску
или Deployment: проверка цепочки владельцев, digest образа и целевой установки ещё
должна быть реализована до подключения этапа к управлению установкой.
Имя context также не закрепляет адрес API-сервера и CA: необходим доверенный
неизменяемый kubeconfig и независимая проверка идентичности кластера.

План без содержимого сессий сохраняется в приватном каталоге и синхронизируется
с файловой системой до создания журнала с его хешем. Далее намерение `isolating`
записывается в журнал **до** добавления собственного уникального finalizer через
JSON Patch с проверкой UID и resourceVersion. Отказ API или тайм-аут после запроса
означают неизвестный результат: план и журнал сохраняются для анализа, успешный
fence не объявляется. Не запускайте операцию повторно по предположению, что запрос
не был выполнен.

Функция `release_unchanged` записывает намерение отмены и удаляет только свой
finalizer, если Pod всё ещё работает с тем же UID, ID контейнера и спецификацией,
без других finalizer. Она не удаляет Pod и не меняет Deployment, PVC или данные.
После операции журнал остаётся в состоянии `aborting`: другие части будущей
транзакции и восстановление всей установки не проверены. При смене объекта,
перезапуске, остановке, исчезновении Pod, node loss, конфликте finalizer либо
неизвестном ответе автоматическое удаление не выполняется и требуется проверка
администратором. Plan и journal должны находиться на доверенной постоянной файловой
системе; владелец каталога, Kubernetes API и узлы входят в границу доверия.
Finalizer сам по себе не предотвращает остановку контейнера или создание нового Pod.
Локальная остановка `kubectl` и его группы не подтверждает отмену уже принятого
сервером запроса; credential-plugin, сознательно покидающий группу процессов,
также находится вне этой гарантии. При любом таком сбое исход остаётся неизвестным.

Будущему механизму ещё нужны подтверждённая приостановка или согласование GitOps и
других контроллеров, ограничения RBAC/admission и доступа к PVC, подтверждение
полного graceful shutdown, безопасное сохранение AOF, контроль конфликта volume,
устойчивый к сбоям rollback и отдельные проверки на каждой стадии. Наблюдение
resourceVersion или наличие finalizer не заменяют ни одну из этих мер.

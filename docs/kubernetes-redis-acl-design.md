# Проект: изоляция Redis ACL для Kubernetes

Это проект нового **отдельного opt-in профиля**, а не инструкция по установке
и не подтверждение безопасности обновления. Он не включён в установщик,
`uterctl` или опубликованный релиз. Новые неподтверждённые операции обслуживания,
backup и обновления не разрешаются, а opt-in восстановление остаётся закрытым.
Существующий путь диагностики и восстановления уже начатых legacy-операций
сохраняется; это не является доказательством полного безопасного восстановления.
Существующая установка и legacy chart должны продолжать работать без нового
профиля и его секретов.

## Что ограничивает текущую реализацию

- Текущий chart запускает Redis с `--requirepass`: отдельные ограниченный
  прикладной пользователь и защищённый admin не созданы. Использование общего
  пароля default не доказывает возможность безопасно запретить только новые
  авторизации прикладного writer.
- `redis_acl_staged.py` и `redis_acl_durable.py` являются экспериментом для
  Compose: проверка подписанного profile привязана к Compose, а работа с ACL
  файлом — к host directory/inode и конкретным UID/GID. Переносить эти
  предположения на Pod или считать результат production fence нельзя.
- Текущий Kubernetes backup перечисляет разрешённые Secret/PVC и сохраняет
  выбранные компоненты. Он не сохраняет и не восстанавливает отдельный admin
  credential и устойчивый ACL state с проверкой их взаимного соответствия.
  Опциональное maintenance-восстановление уже закрыто отдельным gate.
- Текущий набор команд `uter-selected-ci` подтверждён только выбранными
  сценариями тестового профиля. Он не является доказанным полным production
  ACL для всех приложений, фоновых задач, версий redis-py и Lua-операций.

## Кандидат на отдельный signed opt-in

До создания любых кластерных ресурсов будущий установщик проверяет подпись,
inventory всего используемого chart и специального Kubernetes ACL profile,
поддержку обеих служб в подписанном manifest, точные digest образов и наличие
полной реализации выбранного ACL-профиля. Подмена адреса registry на Nexus
допустима только при неизменном подписанном digest. В profile отдельно
фиксируются схема, роли и разрешённые команды, а не пароль. Пока не утверждены
формат capability, chart и закрытый граф подписанного executor, включать opt-in
или выдавать результат `safe_to_backup/update` нельзя.

Для новой установки предполагаются независимые криптослучайные credentials:

1. **writer** ограничен командами и областями ключей, действительно нужными
   проверенной версии Uter; default отключён. Guardrail получает username и
   пароль штатным защищённым способом. Agent получает их только если его
   конкретная версия действительно использует Redis.
2. **admin** отдельный от всех приложений, с минимально необходимыми правами
   для выбранного механизма. Его пароль не передаётся приложению и не
   монтируется в Pod Guardrail/Agent или командную строку. Администратор,
   control plane, узлы, CSI и сами Redis и executor входят в явную модель
   доверия; от скомпрометированного доверенного admin этот профиль не защищает.
3. В Redis ACL файле хранятся только password hashes; сами hashes тоже считать
   конфиденциальными. Секреты не выводятся в stdout, диагностические ошибки,
   argv, объект Pod или CI-артефакты. Не использовать секрет maintenance,
   JWT, audit либо прежний Redis-пароль повторно.

Подготовка Secret должна быть отдельно проверяема и не запускать workloads.
До любого применения сверить namespace, точные имена, тип и поля Secret,
независимость ключей, отсутствие конфликтующих ресурсов и подписанный профиль.
Выдать capability только после закрытия остальных пунктов этого документа;
успешное создание Secret не является разрешением на backup или обновление.
Шифрование Secret в etcd, RBAC и политика допуска к API обеспечиваются и
проверяются в рамках доверенной конфигурации кластера, а не самим Helm chart.

## Почему обновления Kubernetes Secret недостаточно

Обновление Secret в API не означает, что Pod уже читает новый файл: kubelet
обновляет проекцию с задержкой; `subPath` вообще не получает такие обновления.
Redis может перезапуститься и прочитать предыдущий файл, в котором writer ещё
включён. Сравнение `resourceVersion`, одно чтение из Pod и retry не образуют
непрерывное ограждение на всём интервале. См. [документацию Kubernetes о
Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).

Кандидат для исследования — отдельный ACL-файл на проверенном устойчивом
томе, который Redis читает **при каждом старте**. Управляющий компонент с
минимальными правами должен публиковать заранее подготовленный OFF-файл
атомарной заменой, выполнять `fsync` файла и каталога и подтверждать фактическое
содержимое, inode/том и идентичность экземпляра до любых последующих мутаций.
Нужно монтировать проверенную директорию, а не закреплённый за старым inode
файл через `subPath`, и доказать, что управляющий компонент меняет именно тот
том и путь, которые использует Redis при следующем запуске. Замена файла не
меняет уже загруженный volatile ACL; его состояние проверяется отдельно.
Нужны проверенная реализация внутри доверенного Pod, контроль доступа к этой
директории и доказательства свойств конкретного CSI/filesystem при crash и
failover; перенос host-side `rename`/`fsync` из Compose здесь не доказателен.
`ReadWriteOnce` сам по себе не гарантирует одного writer и не обеспечивает
защиту от записи после монтирования; [документация Kubernetes о PV](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)
описывает эти ограничения. `ReadWriteOncePod` можно рассматривать только при
поддержке CSI, но он не заменяет модель доверия и проверку работающих контейнеров.

Bootstrap должен отличать новую пустую установку от потери или отката состояния.
Init container не должен перезаписывать существующий OFF-файл исходным ON при
пересоздании Pod. Потеря PVC, неизвестный исход атомарной записи, несовпадение
PV/PVC, возврат старого snapshot или повреждённый ACL приводят к остановке без
автоматического включения writer. Если это нельзя обеспечить до запуска Redis,
профиль остаётся недоступным. Одной атомарной записи недостаточно без защиты от
отката тома и проверки доступности соответствующего admin credential.

## Порядок будущей операции и recovery

Сохранить существующий доверенный lock, HMAC journal, signed scope и проверки
идентичности, но не считать их сами по себе fence. Сначала необходимо
подтвердить полный набор replicas и закрыть новые источники запросов; затем для
Redis определить единственный доверенный admin-сеанс, актуальные run_id и Pod,
ACL users и разрешения, отсутствие иных writers, кроме подтверждённого набора
действующих writer-сессий, а также репликации, модулей и фоновых процессов,
способных менять данные. Модель сети, admission/RBAC и поведения при
замене Pod должна быть проверена отдельно.

Планируемая последовательность с устойчивыми intent/receipt:

1. Под устойчивым lock подготовить и подтвердить **долговечный OFF** на томе,
   сохранив volatile ACL ON до начала операции. Этот шаг не утверждает наличие
   fence и не допускает backup.
2. В живом Redis для конкретного writer отключить новые AUTH, не прерывая уже
   прошедшие авторизацию соединения; зафиксировать и проверить результат. По
   [контракту Redis](https://redis.io/docs/latest/commands/acl-setuser/) смена
   пользователя на `off` не закрывает уже существующие соединения.
3. Выполнить protocol drain Agent → Guardrail с идентификацией каждого процесса
   и подтверждением аудита. При любом рестарте/неизвестном исходе остановиться;
   в частности, Redis ACL не запрещает запись в audit вне Redis.
4. После доказанного drain закрыть оставшиеся writer соединения и проверить
   Redis identity, все подключения и ACL. Проверить устойчивый OFF и защиту
   от рестарта/замены ещё раз. Только независимая реализация, удерживающая все
   требуемые ограничения непрерывно, может впоследствии разрешать backup.
   [CLIENT KILL](https://redis.io/docs/latest/commands/client-kill/) не прерывает
   команду, которая уже выполняется; закрытие сокета не доказывает, что ранее
   запущенная работа и аудит завершены.

Потеря ответа об OFF/KILL, смена Redis run_id или Pod, недоступность API,
конфликтующий controller, непроверенное состояние тома, другая admin-сессия
или writer требуют сохранения journal и ручной/отдельно проверенной процедуры
восстановления. Нельзя автоматически повторить мутацию, включить writer или
приравнять новое admin-соединение к прежнему. История с неоднозначными alias
остаётся отдельно заблокирована.

## Backup и восстановление credentials и ACL

Нужен единый аутентифицированный backup scope: установка/кластер/namespace,
operation ID, signed manifest и ACL profile, UID объектов, версия состояния,
хеш ACL файла и идентичность Redis должны совпадать во всех компонентах и
receipt. Admin credential должен сохраняться в защищённой зашифрованной capsule
или ином проверенном credential store; его восстановление необходимо проверить
до начала операции. Разрабатываемая для Compose экспериментальная capsule
привязана к Compose profile и не удостоверяет Kubernetes chart, mount или fence;
для Kubernetes нужен собственный проверенный signed profile и явная привязка.

Восстановление создаёт отдельные ресурсы в новой изолированной области и сначала
проверяет подпись, целостность, права, Secret, ACL hashes и соответствие capsule.
Восстановленный Redis должен стартовать с **OFF**, а не с историческим ON,
пока нет доказанного решения о безопасном допуске writers. Компонент ACL должен
быть учтён явно: восстановление одного RDB не восстанавливает ACL-файл на PVC.
Замену имён namespace/Secret выполнять согласованно, не менять исходные данные;
неизвестный исход и несовпадения блокируют продолжение. Старое состояние или
устаревший backup не должны тайно отменять ранее зафиксированный OFF. Если
невозможно подтвердить неизменность и монотонность состояния, автоматическое
восстановление остаётся закрытым. Согласованность компонентов одного backup не
доказывает его свежесть: одновременный откат PVC и локального journal должен
обнаруживаться независимой защищённой authority/epoch вне общего домена отката;
при отсутствии такой authority требуется отказ, а не предположение о свежести.

## Необходимые испытания до подключения

- Unit/property тесты для signed profile, Secret fields, distinct credentials,
  отказов до создания ресурсов, проверок capsule/manifest/ACL и legacy без opt-in.
- Изолированный kind или отдельный Kubernetes-кластер: реальные новые образы,
  отдельный admin и writer, выбранный CSI, проверка разрешений и реальных путей
  приложений Redis. Никаких локальных существующих workloads.
- Падение до/после каждого intent, `fsync`, замены ACL файла, OFF, KILL и receipt;
  restart контейнера Redis и замена Pod/тома, задержанная проекция Secret,
  недоступный API/CSI, восстановление устаревшего snapshot, конфликтная admin
  сессия и неизвестные writers. Проверять фактическую невозможность новой
  авторизации и сохранение работы прежнего соединения до drain.
- Проверка полного backup и восстановления OFF в отдельный namespace с
  зашифрованной capsule; тесты потери, подмены и несоответствия ACL/admin/writer.
  Проверка содержимого Redis, audit chain и непрерывности допуска writers после
  разрешённого восстановления.
- Проверка процессов Guardrail/Agent и аудита при рестартах на всех фазах;
  durable ACL Redis сам по себе не доказывает durable maintenance Uter. Для
  альтернативного изменения Uter см. [задание на устойчивый epoch](uter-durable-maintenance-task.md).

Только после этих работ и независимого security-review можно решать вопрос о
подключении к `uterctl`; этот документ не меняет действующие защитные gates.

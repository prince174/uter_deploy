# Подписанное обновление и восстановление

Команды ниже работают на Linux и предназначены для установки `install.py`, принятой
под управление `uterctl`. Используйте **проверенный подписанный комплект**, содержащий
контроллер и скрипты. Настоящий переход разрешён только если новая версия подписана
доверенным ключом, содержит текущую версию в `upgrade_from` и имеет совместимый
`data_epoch`. Тестовые ключи и версии CI для эксплуатации не подходят.

## Доверие и подготовка комплекта

Получите публичный ключ издателя и его SHA256 по независимым доверенным каналам.
Сверьте отпечаток PEM-файла с заранее полученным значением; ключ, скачанный только
вместе с архивом, не подтверждает его подлинность. Затем подготовьте Python 3.11+
и зависимости `requirements.txt` из доверенного репозитория и выполните:

```bash
python3 scripts/extract_signed_bundle.py --archive /path/to/signed-bundle.tar.gz \
  --key /path/to/trusted-publisher.pem --output /srv/uter-bundles/VERSION
```

Родитель выходного каталога должен существовать, сам каталог должен быть новым.
Команда проверит подпись и содержимое перед предоставлением комплекта; `INCOMPLETE`
означает незавершённую операцию. Архивный checksum выявляет повреждение, но не
заменяет проверку подписи и доверенного ключа.

## Принятие установки под управление

Скачайте **подписанный комплект текущей установленной версии** и убедитесь, что он
совпадает с запущенными образами и шаблонами. На машине установки:

```bash
sudo /path/to/venv/bin/python /path/to/current-bundle/scripts/adopt_managed.py \
  --home /srv/uter-instance --bundle /path/to/current-bundle \
  --publisher-key /path/to/trusted-publisher.pem
```

Для Kubernetes используйте ту же команду с путём его каталога установки. Нужны
доступ к указанному в конфигурации kube-context и `kubectl`. Команда проверяет
работающие образы, подпись, шаблоны и запрос к LLM. Она сохраняет состояние
контроллера и команду проверки, не меняя запущенные рабочие ресурсы. LLM-запрос
может расходовать квоту выбранного провайдера.

## Обновление

Создайте два отдельных защищённых каталога вне установки и отдельно сохраните ключ
копии. В примере команды выполняются от root, поэтому каталоги должны принадлежать
root; для Kubernetes без sudo владельцем должен быть запускающий пользователь.

```bash
sudo install -d -m 700 -o root -g root /srv/uter-backups /srv/uter-backup-keys
sudo /path/to/venv/bin/python /path/to/new-bundle/scripts/update_installation.py \
  --home /srv/uter-instance --bundle /path/to/new-bundle \
  --publisher-key /path/to/trusted-publisher.pem \
  --backup-root /srv/uter-backups --backup-key /srv/uter-backup-keys/backup.key \
  --create-backup-key
```

`--create-backup-key` нужен только при **первом** создании ключа. Повторно передавать
его для существующего ключа нельзя: замена ключа заблокирована. При первом обновлении
ещё не принятой установки добавьте `--current-bundle /path/to/current-bundle`; при
необходимости команда сначала примет установку под управление. При сбое проверяйте
состояние и журнал, не удаляйте каталоги или volumes для повтора.

Контроллер проверяет подпись и переход, временно останавливает пишущие компоненты,
создаёт и проверяет зашифрованную копию, обновляет сервисы и выполняет проверку с LLM.
На время копирования убедитесь, что внешние приложения или операторы не записывают
данные напрямую в Redis и том аудита: контроллер останавливает только компоненты Uter.
Ключ не входит в копию; без него восстановление невозможно. Разместите копию и
защищённую копию ключа на независимом от установки хранилище и отдельно проверяйте
их восстановимость. В базовой проверке размер снимка Redis ограничен 100 МиБ.

## Восстановление Compose в новый проект

Нужны резервная копия, её ключ, независимо доверенный ключ издателя, прежний
**абсолютный путь** установки и доступ к подписанному комплекту и образам. Для
безопасности восстановление создаёт **новые** каталог, Compose-проект и тома;
старые не перезаписываются. Выберите свободные имя и локальный порт:

```bash
sudo /path/to/venv/bin/python /path/to/signed-bundle/scripts/recover_compose.py \
  --source-home /srv/uter-instance --backup /srv/uter-backups/uter-BACKUP \
  --backup-key /srv/uter-backup-keys/backup.key \
  --publisher-key /path/to/trusted-publisher.pem \
  --home /srv/uter-recovered --name uter-recovered --port 18001
```

Родитель нового каталога должен существовать, а сам каталог, проект и тома — нет.
Команда проверяет копию, подпись, RDB и доступность образов, восстанавливает Redis и
аудит в пустые тома, создаёт AOF из загруженного RDB, запускает сервис и проверяет
его с LLM. `recovery-operation.json` фиксирует этап; при ошибке новые ресурсы
сохраняются для диагностики, исходная установка не переключается автоматически.

## Восстановление Kubernetes в новый namespace

На машине с `kubectl`, Helm и доступом к целевому кластеру выберите новый namespace,
свободный локальный порт для проверки и новый каталог:

```bash
/path/to/venv/bin/python /path/to/signed-bundle/scripts/recover_kubernetes.py \
  --source-home "$HOME/uter-k8s" --backup /path/to/uter-BACKUP \
  --backup-key /path/to/backup.key --publisher-key /path/to/trusted-publisher.pem \
  --home "$HOME/uter-recovered" --name uter-recovered \
  --context MY_CONTEXT --port 18001
```

Нужны права создавать namespace, Secret, ConfigMap, PVC, Pod и ресурсы Helm;
CSI должен выдавать новые тома. При смене StorageClass передайте
`--storage-class NAME`. Восстанавливаются сохранённые Secret/ConfigMap, Redis и
аудит; проверяются запуск и запрос к LLM. Поддерживается базовая конфигурация со
встроенными моделями; внешний model PVC требует отдельной процедуры.

## Перед переключением трафика

Восстановление соответствует **моменту создания копии**. Записи после него в
восстановленной установке отсутствуют. До переключения остановите приём новых записей
в исходной установке, согласуйте окно и проверьте полноту нужных данных. Подключите и
проверьте внешний LLM, TLS/Ingress, обратный прокси, сетевые политики и внешние
хранилища отдельно: они не восстанавливаются этой командой. Переключение трафика и
очистка старой установки остаются осознанными действиями оператора.

## Границы резервной копии и проверка на отдельном стенде

Копия включает данные и конфигурацию, перечисленные выше: Redis, аудит, runtime и,
для Kubernetes, относящиеся к установке Secret/ConfigMap. Это не полная копия всего
окружения: внешние базы и RAG-хранилища, PVC дополнительных моделей, LLM-провайдер,
DNS, сертификаты, ingress и внешние секреты нужно резервировать и восстанавливать
отдельно средствами соответствующей системы. Зафиксируйте общий момент копирования,
проверьте согласованность с копией Uter и отдельно выполните проверку интеграций.
Скрипт не меняет DNS, ingress или прокси и не удаляет старую установку.

Изменение на потоковую проверку находится в текущем репозитории и будет доступно
в новом подписанном комплекте. Опубликованные комплекты `deploy-2026.10.29-signed-4`
(0.1.6) и `deploy-2026.10.30-gated-2` (предварительная 0.1.7) ещё используют
временный файл в `/tmp` Redis; в Kubernetes этот каталог может размещаться на
диске узла. Учитывайте это при защите узлов и резервных данных.

Размер RDB в текущей реализации ограничен 100 МиБ. Для проверки содержимое
расшифровывается непосредственно в поток `redis-check-rdb` внутри контейнера
Redis: отдельный файл снимка в `/tmp` не создаётся, вывод проверяющей команды
подавляется. Данные при этом проходят через оперативную память; защита от swap,
дампов памяти и доступа привилегированного администратора зависит от окружения.
Каталог резервной копии и его владелец должны оставаться доверенными: поток
расшифровки передаётся проверяющей программе до окончательной проверки тега GCM;
ошибка проверки не разрешает завершить резервное копирование. При обрыве связи
завершение локального `docker` или `kubectl` не доказывает завершение удалённого
`redis-check-rdb`; администратору может понадобиться проверить контейнер.
При превышении лимита обновление останавливается до замены сервисов; увеличение
значения вручную не проверено. Потоковая проверка не заменяет пробное восстановление.
Для больших баз нужен отдельно проверенный способ потоковой обработки с контролем
ресурсов. Не считайте эту возможность доступной.

Изменённая потоковая проверка прошла [сценарий резервного копирования и
восстановления в Compose и Kubernetes](https://github.com/prince174/uter_deploy/actions/runs/41046089186)
на одноразовых CI-стендах с тестовыми подписями и данными. Это не проверка
успешного перехода опубликованных версий 0.1.6 → 0.1.7.

Проверка вне CI требует **отдельного** Linux-хоста или VM с собственным Docker daemon;
для Kubernetes — отдельного кластера и свободных namespace, диска и портов. Общий
Docker Desktop и общий кластер не изолируют ресурсы от других работающих установок.
На таком стенде:

1. Установите Uter по README из опубликованного подписанного выпуска, используя тестовые
   учётные записи и LLM, и проверьте работу и доступность данных.
2. Получите следующий выпуск, проверьте его подпись и допустимость перехода. Выполните
   обновление по разделу «Обновление», сохранив резервную копию и её ключ отдельно.
3. Восстановите копию в новый проект Compose или namespace Kubernetes командами выше;
   проверьте LLM, аудит и необходимые данные. Проверьте отдельно внешние интеграции.
4. Зафиксируйте версии, результаты и время восстановления. Удаляйте только ресурсы,
   созданные для этого теста, убедившись в их имени и принадлежности.

Прохождение изолированного GitHub Actions не заменяет такую проверку на целевой
инфраструктуре. На общем Docker Desktop она в рамках этой проверки не проводилась.

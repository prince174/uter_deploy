# Проверка изоляции записи Redis

Этот материал описывает разработку, а не готовую процедуру обновления. Барьер
`0.1.6 → 0.1.7` остаётся закрытым; ни экспериментальный CI, ни журнал сами по
себе не дают разрешения переносить данные.

Проверяется жизненный цикл изоляции: сначала останавливаются штатные писатели,
затем ограничиваются внешние подключения и закрываются старые соединения. Только
после этого допустимы контроль состояния Redis и резервная копия. При проверке
перезапуска важно сохранить не только RDB: штатный Redis использует AOF. После
ошибки компоненты должны оставаться изолированными либо вернуться к старому
состоянию только после явной проверки; произвольный результат команды нельзя
считать успешным восстановлением.

`scripts/redis_fence_journal.py` — отдельный строительный блок для фиксации
этапов, ещё не подключённый к обновлению. Журнал хранит случайный идентификатор
операции, тип платформы, идентификатор установки и ресурса, хеш плана и стадию;
пароли, историю и параметры подключения в него не записываются. Запись выполняется
через приватный файл и `fsync`. Вызывающая сторона обязана удерживать общую
исключительную блокировку установки и проверить действие отдельно: одна запись
`isolated` не доказывает, что Redis изолирован. Ошибка `fsync` означает
неопределённый результат: перед продолжением требуется проверка состояния.

При сбое в любой незавершённой стадии допустим переход в `aborting`, затем в
`restored` только после проверки фактического восстановления. При сбое во время
создания возможна оставшаяся временная жёсткая ссылка; в этом случае чтение журнала
откажет и понадобится ручная проверка. Каталог, его родители, владелец и система
блокировки должны быть доверенными. Схема восстановления сети, контроллеров и
конфигурации для реальной установки ещё не реализована в этом журнале.

Защита предполагает доверенные хост и Docker-администратора для Compose, а для
Kubernetes — доверенные control plane, узлы и администраторов. Доступ через
привилегированный `exec`, изменение ресурсов сторонним контроллером или повторное
подключение тома требует отдельного контроля. Заглушка источника владельцев истории
не считается доказательством и не снимает защитную блокировку.

В [синтетическом Compose CI](https://github.com/prince174/uter_deploy/actions/runs/41049819951)
проверены закрытие старого TCP после отключения сети и завершения клиентов,
выключение политики перезапуска, перезапуск Docker и сохранение тестовой записи
AOF при запуске изолированного и прежнего Redis. Отсутствие нового соединения
проверялось в ограниченном временном окне. Это не проверка аварийного восстановления
установки с помощью журнала.

В [синтетическом Kubernetes CI](https://github.com/prince174/uter_deploy/actions/runs/41050552379)
проверены ограниченный loopback bind после Recreate, старое TCP-соединение,
перезапуск, тестовый AOF и отказ при намеренно прерванной остановке. Отдельный
сценарий использовал тот же образ Redis и команду PID 1, что опубликованы для
0.1.6, с наблюдением завершения старого Pod через тестовый finalizer; это не
установка подписанного Helm chart и не доказательство работы для другого кластера.
Проверка принудительного удаления использует известный тесту признак принуждения;
автоматическое обнаружение всех способов принудительного завершения не реализовано.

`scripts/compose_fence_protocol.py` описывает экспериментальный порядок стадий;
реального Docker-адаптера он не содержит. `scripts/compose_redis_diagnostic.py`
проверяет некоторые признаки Compose только для явно выбранной установки и не
проверяет клиентов Redis, не изолирует сеть и не разрешает обновление. Тесты этой
диагностики используют моки; на работающем стенде она не запускалась.

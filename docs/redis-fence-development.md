# Проверка изоляции записи Redis

## Подготовка протокола обслуживания Uter

Изменения Uter из коммитов `f7f1290` и `500ff6c` определяют протокол
обслуживания: сначала Agent, затем Guardrail, проверка завершения запросов,
аудита и закрытия Redis-клиента. Подтверждение процесса не заменяет сетевую
изоляцию Redis и не разрешает миграцию истории.

В текущем дереве подготовлены ограниченные компоненты для проверки receipt,
координации реплик, записи HMAC-подтверждений и вызова через exec. Поддержка
протокола должна быть явно объявлена в **подписанном** манифесте установленного
релиза; старые образы без объявления не принимаются за поддерживающие протокол.
Наличие объявления само по себе не доказывает поведение образа или изоляцию.
Эти компоненты пока не подключены к пользовательскому обновлению `uterctl`,
не блокируют изменения установки сами по себе и не входят в выпущенный релиз.
Нельзя вызывать их как процедуру обновления действующей установки.

В рабочем дереве команда `maintenance-check-compose` выполняет только чтение
состояния обоих процессов установленного Compose через `GET`, сверяя подписанную
поддержку протокола и идентичность контейнеров. Успех означает лишь, что проверка
доступности прошла: результат всегда содержит `safe_to_update: false` и
`redis_isolated: false`. Она не останавливает входящий трафик, не блокирует
перезапуск процессов и не создаёт резервную копию.

В этом дереве начало новых экспериментальных операций `fence-start-redis` и
`apply --fenced-update` временно запрещено с ошибкой
`COMPOSE_MAINTENANCE_ISOLATION_UNAVAILABLE`. Прежняя остановка с обычным SIGTERM
не подтверждает завершение запросов и сохранность аудита. Для снятия запрета
необходимы подтверждённая изоляция входящего трафика и перезапусков, проверка
подтверждений обслуживания, изоляция всех внешних писателей Redis и проверенное
восстановление. Команды восстановления ранее начатых операций сохраняются;
не удаляйте их журналы вручную. Это ограничение относится к текущему коду и
само по себе не изменяет поведение уже опубликованных релизов.

**Исполнитель для восстановления:** экспериментальная операция привязана к
SHA-256 файла `checksums.json` того подписанного комплекта исполнителя, которым
она начата. Для её завершения сохраните и используйте тот же полный подписанный
комплект и его доверенный открытый ключ; новый подписанный комплект с другим
хешем не является заменой и будет отвергнут. Не заменяйте `checksums.json`, не
исправляйте журналы вручную и не считайте совпадение одного файла достаточной
проверкой: контроллер также проверяет подпись и файлы исполнителя. Если исходный
комплект недоступен, автоматическое завершение не подтверждено; сохраните данные
и журналы для разбора. Старый исполнитель не содержит новую блокировку начала
операций: используйте его только для соответствующей процедуры восстановления,
а не для запуска новых операций.

Подготовлен отдельный disposable CI для проверки подтверждений настоящих
собранных образов Uter с Redis в Compose. Результат этого CI не является
проверкой полной изоляции Redis, резервной копии или восстановления. Для
Kubernetes и перехода `0.1.6 → 0.1.7` эти условия остаются отдельными задачами.

Экспериментальная ветка same-epoch Compose использует подписанный исполнитель,
зашифрованную копию и отдельное решение `mutation`. Часть механики проверена в
одноразовом CI на искусственных образах; полный сценарий для настоящих образов
не подтверждён. Она отсутствует в опубликованных релизах.
Старые контроллеры и параллельную Docker-автоматику одновременно использовать
нельзя. Источник владельцев истории остаётся заглушкой; переход между epoch и
обновление `0.1.6 → 0.1.7` этим путём не разрешаются.

Состояние проверок на 30 октября 2026 года:

- [Проверка остановки Guardrail](https://github.com/prince174/uter_deploy/actions/runs/41081802242)
  прошла в отдельной установке с настоящими образами и тестовым LLM upstream.
  Проверены авторизация и запрос до и после остановки, HMAC и сохранение префикса
  журнала аудита, а также наличие тестовой записи и статус AOF в работающем
  Redis. Guardrail завершился с кодом из класса `TERM_LIKE`. Во время остановки
  запросов не подавали: эта проверка не доказывает завершение запросов в полёте,
  фоновых задач, полноту аудита или сохранность AOF при отказе питания.
- [Проверка экспериментального `apply --fenced-update`](https://github.com/prince174/uter_deploy/actions/runs/41081997614)
  **не прошла**: на этапе `prepared` проверка остановки Guardrail обнаружила
  `TERM_LIKE`, без признака OOM, и обновление остановилось до снимка и запуска
  целевых writers. Два комплекта для этого испытания были подписаны временным
  тестовым ключом и содержали одинаковые образы и epoch; это не проверка смены
  версии приложения и не обновление опубликованного `0.1.6 → 0.1.7`.
- В [отдельном механическом испытании Compose](https://github.com/prince174/uter_deploy/actions/runs/41085465178)
  все три задания прошли на одноразовых runner с локальным registry. Guardrail и
  Agent использовали искусственные тестовые образы: обёртка намеренно возвращает
  нулевой код после SIGTERM дочернего процесса. Для старой и новой тестовых версий
  применялись разные digest и временные подписи; Redis оставался исходным.
  Проверены три случая:

  1. Подписанный `apply` прошёл со сменой тестовых образов, зашифрованной копией,
     прежними Redis container/процессом/endpoint/томом и сохранённым тестовым ключом;
     запрос проверялся с тестовым LLM upstream.
  2. После SIGKILL на `target_starting` подписанный `fence-finish-update` отказал,
     сохранив managed lock и journal. Отправленный Docker-запрос мог ещё выполняться;
     тест не разрешает повторять запуск или восстанавливать старую копию.
  3. При искусственном аварийном завершении непосредственно перед заменой
     `state.json` подписанный `fence-finish-update` проверил состояние, сам
     восстановил managed lock и закончил операцию. Тест вручную lock не удалял;
     Redis и зашифрованная копия сохранились.

  Эти тесты подтверждают только перечисленные переходы механизма на синтетических
  writers. Они не подтверждают drain настоящих образов, работу с реальной LLM,
  аварийную устойчивость произвольного хранилища, все возможные моменты сбоя или
  миграцию истории `0.1.6 → 0.1.7`.
- [Отдельная проверка очистки после обновления](https://github.com/prince174/uter_deploy/actions/runs/41086780123)
  на тех же искусственных writers прошла для трёх выбранных точек SIGKILL: после
  удаления первого и последнего файла evidence, а также после удаления journal
  при сохранённом HMAC cleanup marker. В каждом случае подписанный
  `fence-finish-update` восстановил managed lock без ручного удаления sentinel
  и завершил проверку; Redis и зашифрованная копия сохранились. При первой
  попытке случай с последним evidence остановился раньше, на создании снимка,
  по неуточнённой причине; повтор того же задания на том же commit прошёл.
  SIGKILL процесса не моделирует отключение питания или отказ `fsync`.
- Отдельные исследования Compose проверяли возврат Redis после аварии до снимка
  и закрытый сценарий снимка и возврата, в частности в [CI до снимка](https://github.com/prince174/uter_deploy/actions/runs/41068344809)
  и [CI подписанной команды снимка](https://github.com/prince174/uter_deploy/actions/runs/41068886608).
  Эти результаты не подтверждают полный экспериментальный `apply`, миграцию
  данных, завершение всех внешних writers или восстановление любой установки.
- После перехода экспериментальных Compose-команд на managed Lease старые
  CI-раунды, вручную удалявшие тестовый PID-файл после SIGKILL, исключены:
  они не проверяют новую блокировку и не входят в текущее регрессионное покрытие.
  Прошлые успешные запуски выше остаются историческими свидетельствами для
  прежнего кода. Неподтверждённые ранние фазы должны оставаться заблокированными;
  пользовательское автоматическое восстановление после аварии до или во время
  снимка с новым Lease пока не подтверждено.
- Для Kubernetes разрабатывается отдельный coordinator: он проверяет остановку
  известных writers, loopback Redis и согласованность конфигурации, шифрует
  резервную копию и связывает её с HMAC receipt и снимком runtime. Проверка
  аудита пока ограничена структурой зашифрованного архива: HMAC-цепочка самого
  журнала не проверяется. Coordinator не подключён к пользовательскому обновлению;
  непрерывная изоляция внешних writers и полное восстановление не подтверждены.

Сетевой барьер и отсутствие открытых соединений сами по себе не доказывают, что
приложение завершило фоновые задачи и записало все события аудита. Для принятия
такого кода завершения нужен проверяемый контракт остановки и подтверждение flush
сервиса; до этого ненулевой код остаётся причиной отказа обновления.

Узкий профиль — Compose на доверенном Linux с локальным Docker, одинаковыми
подписанными `compose.yaml` и `empty.env`, Redis digest, полным каноническим
конфигом кроме образов двух writers и публичными образами. Redis, его netns,
endpoint и volume проверяются до и после запуска целевых writers. Трафик и новые
записи возможны уже после снятия изоляции Redis. С этого момента нельзя
автоматически восстанавливать старый снимок поверх новых данных.

Для диагностики используйте `python -I /путь/к/подписанному/uterctl.py fence-status --home /абсолютный/каталог`.
Это состояние файлов, а не проверка
действующей изоляции. При `capturing`, `snapshot_releasing` или
`target_starting`, неполных evidence, наличии finalize anchor либо неясном
исходе процесса не повторяйте запуск, не удаляйте маркеры и не восстанавливайте
копию поверх работающих данных: требуется ручная проверка оператором.

Только при фазе `target_running` или `update_finalizing` экспериментальная
команда `fence-finish-update` повторно проверяет подписанные source/target,
backup, Redis и работающие target writers и завершает две записи состояния и
уборку, если все evidence сохранились и совпадают. Если при уборке создан
аутентифицированный `compose-fenced-cleanup.json`, повторная команда может
проверить сохранённое доказательство, состояние, backup и живые ресурсы и
продолжить даже после удаления части evidence или самого journal. Она вызывается тем же
изолированным подписанным исполнителем с `--home`, `--bundle` (абсолютный путь
к уже установленному target в `home/releases/<версия>`), `--key`,
`--executor-key`, `--backup-key` и `--backup-dir`. При отказе проверок команда
оставляет данные и evidence для разбора; она не перезапускает writers и не
восстанавливает снимок. Экспериментальные fence-команды используют проверяемую
managed lease; после SIGKILL `fence-finish-update` может забрать только lease
достоверно завершившегося владельца, повторно проверив HMAC evidence до и после
flock. Это разрешено лишь в `target_running`, `update_finalizing` либо для
аутентифицированного sealed cleanup. Другие и неизвестные исходы остаются
заблокированы: гибель процесса не подтверждает завершение отправленного Docker
или API вызова. Старый PID-only `operation.lock` автоматически не удаляется и
требует ручной проверки. Обычные backup-команды пока используют прежний O_EXCL.
Новая схема требует доверенного хоста, полного host PID namespace и локальной
файловой системы; signed hosted CI интеграции ещё необходим. Дефект
хранилища может сделать сохранение маркеров ненадёжным, в том числе при ошибке
fsync после удаления последнего маркера; старый исполнитель не знает новые
маркеры.

Этот материал описывает разработку, а не готовую процедуру обновления. Барьер
`0.1.6 → 0.1.7` остаётся закрытым; ни экспериментальный CI, ни журнал сами по
себе не дают разрешения переносить данные.

Проверяется жизненный цикл изоляции: сначала останавливаются штатные писатели,
затем ограничиваются внешние подключения и закрываются старые соединения. Только
после этого допустимы контроль состояния Redis и резервная копия. При проверке
перезапуска важно сохранить не только RDB: штатный Redis использует AOF. После
ошибки компоненты должны оставаться изолированными либо вернуться к старому
состоянию только после явной проверки; произвольный результат команды нельзя
считать успешным восстановлением.

`scripts/redis_fence_journal.py` — отдельный строительный блок для фиксации
этапов, ещё не подключённый к обновлению. Журнал хранит случайный идентификатор
операции, тип платформы, идентификатор установки и ресурса, хеш плана и стадию;
пароли, историю и параметры подключения в него не записываются. Запись выполняется
через приватный файл и `fsync`. Вызывающая сторона обязана удерживать общую
исключительную блокировку установки и проверить действие отдельно: одна запись
`isolated` не доказывает, что Redis изолирован. Ошибка `fsync` означает
неопределённый результат: перед продолжением требуется проверка состояния.

Текущие исходники контроллера и мастера, а также создание резервной копии,
отказываются начинать изменяющую операцию при наличии
`redis-fence-operation.json`, даже если это повреждённый файл или символическая
ссылка. Это защитная проверка, а не подключение fence к обновлению. Ранее
опубликованные подписанные контроллеры, включая 0.1.6, об этом журнале не знают;
нельзя полагаться на их отказ после прерванного эксперимента. Текущие изменения
в опубликованный комплект ещё не вошли.

В текущем исходном коде `uterctl.py fence-status --home ПУТЬ_УСТАНОВКИ`
показывает запись, прошедшую проверку формата и прав доступа, либо её отсутствие. Команда не
изменяет установку и не проверяет фактическое состояние Redis или сети; отсутствие
журнала не доказывает, что установка безопасна. Повреждённый журнал и ссылка
вместо файла приводят к ошибке. Команда будет доступна пользователю только после
включения этого кода в новый подписанный комплект.

В текущем исходном коде разрабатывается ограниченная Compose-команда
`fence-resume-writers`: она допускает только исходные остановленные контейнеры,
привязанные к аутентифицированному start-intent, проверяет подписанный комплект,
Redis и, если снимок создавался, полную резервную копию и решение `release`.
До первого запуска сохраняются отдельный аутентифицированный resume-intent и
стадия `writers_resuming`. Затем запускаются исходные контейнеры и проверяется
их Docker health; пользовательские запросы для smoke не отправляются. При ошибке
или неизвестном результате команда не повторяет запуск, не останавливает
контейнеры и не восстанавливает старую копию. После успеха фиксируется
`writers_resumed`, но журнал и другие свидетельства пока сохраняются; это ещё
не готовая процедура обновления и не финализация установки.

Как только снято сетевое правило Redis, внешние подключения уже могут выполнить
новые записи. При запуске Guardrail трафик также может поступить до завершения
health-проверки. Поэтому старый снимок нельзя автоматически накатывать поверх
действующей установки после снятия изоляции или начала запуска writers: сначала
потребовалась бы новая изоляция и проверка данных. `writers_resuming` не означает,
что оба контейнера остановлены; при сбое один или оба могут уже работать.

Экспериментальная отдельная команда `fence-finalize` предназначена только для
стадии `writers_resumed`: она повторно проверяет подписи, идентичность и health
исходных контейнеров, Redis, сохранённые аутентифицированные записи и, если она
создавалась, резервную копию. Перед очисткой записывается стадия `finalizing`,
затем удаляются только проверенные записи, а блокирующий журнал — последним.
Сама копия не удаляется и не восстанавливается. Сбой или неопределённая частичная
очистка сохраняет `finalizing` для разбора; повтор автоматически не допускается.
Эта команда находится в разработке и не заменяет проверку полного обновления.

Для последнего удаления используется дополнительный блокирующий hardlink
`compose-fence-finalize-anchor.json`: он сохраняет блокировку, если журнал уже
удалён, но синхронизация каталога или возврат исходного имени не удались. Новые
команды проверяют оба имени, включая повреждённые файлы и ссылки. Ранее
опубликованные инструменты об anchor не знают и не должны запускаться параллельно.
После успешной синхронизации удаления журнала anchor удаляется отдельно: если
последующий `fsync` завершился ошибкой и оба имени уже отсутствуют, функция
сообщит ошибку, но блокирующего имени в текущем состоянии может не быть;
автоматического восстановления старой копии она не выполняет. При неисправном
хранилище нельзя гарантировать успешную запись или восстановление любого маркера.

Стадия `redis_released` сама по себе не говорит, создавался ли снимок. До
снятия правила сохраняется отдельная HMAC-запись происхождения release: до
снимка либо после проверки снимка с хешем receipt. При отсутствии или порче
этой записи, а также при отсутствии snapshot receipts для второго случая,
запуск writers отказывает; отсутствие файлов не считается доказательством
того, что снимка не было. Старые эксперименты без origin автоматически не
переводятся в новый формат.

Допустимые переходы при сбое зависят от текущей стадии и перечислены в журнале.
Стадия `redis_released` фиксирует проверенный возврат сети и политики Redis;
для различения возврата до снимка и после него используется отдельная
аутентифицированная запись происхождения. Эта стадия не означает восстановления
Guardrail, Agent и всей установки.
`restored` допустима только после проверки фактического восстановления всех
необходимых компонентов. При сбое во время
создания возможна оставшаяся временная жёсткая ссылка; в этом случае чтение журнала
откажет и понадобится ручная проверка. Каталог, его родители, владелец и система
блокировки должны быть доверенными. Схема восстановления сети, контроллеров и
конфигурации для реальной установки ещё не реализована в этом журнале.

Для будущего восстановления проверяется отдельная экспериментальная блокировка
с аутентифицированными метаданными и совместимым PID-файлом. В [одноразовом Linux
CI](https://github.com/prince174/uter_deploy/actions/runs/41063292805) проверены
SIGKILL владельца, передача блокировки и конкурентные попытки старого O_EXCL.
Это свидетельство для одного окружения: модуль не подключён к `uterctl`, не
подтверждает завершение запросов к Docker или Kubernetes и не гарантирует полную
видимость процессов или семантику файловой системы на другом хосте.

Защита предполагает доверенные хост и Docker-администратора для Compose, а для
Kubernetes — доверенные control plane, узлы и администраторов. Доступ через
привилегированный `exec`, изменение ресурсов сторонним контроллером или повторное
подключение тома требует отдельного контроля. Заглушка источника владельцев истории
не считается доказательством и не снимает защитную блокировку.

В [синтетическом Compose CI](https://github.com/prince174/uter_deploy/actions/runs/41049819951)
проверены закрытие старого TCP после отключения сети и завершения клиентов,
выключение политики перезапуска, перезапуск Docker и сохранение тестовой записи
AOF при запуске изолированного и прежнего Redis. Отсутствие нового соединения
проверялось в ограниченном временном окне. Это не проверка аварийного восстановления
установки с помощью журнала.

В [синтетическом Kubernetes CI](https://github.com/prince174/uter_deploy/actions/runs/41050552379)
проверены ограниченный loopback bind после Recreate, старое TCP-соединение,
перезапуск, тестовый AOF и отказ при намеренно прерванной остановке. Отдельный
сценарий использовал тот же образ Redis и команду PID 1, что опубликованы для
0.1.6, с наблюдением завершения старого Pod через тестовый finalizer; это не
установка подписанного Helm chart и не доказательство работы для другого кластера.
Проверка принудительного удаления использует известный тесту признак принуждения;
автоматическое обнаружение всех способов принудительного завершения не реализовано.

`scripts/compose_fence_protocol.py` описывает экспериментальный порядок стадий;
реального Docker-адаптера он не содержит. `scripts/compose_redis_diagnostic.py`
проверяет некоторые признаки Compose только для явно выбранной установки и не
проверяет клиентов Redis, не изолирует сеть и не разрешает обновление. Тесты этой
диагностики используют моки; на работающем стенде она не запускалась.

Экспериментальный `scripts/compose_fence_recovery_plan.py` сохраняет приватный
план с MAC и идентификатором операции; он не выполняет восстановление и не
доказывает, что сеть, IP и aliases удастся воссоздать. Для проверки отключения
сети создан экспериментальный Docker-адаптер, но штатная сеть с автоматически
выделенным адресом не гарантирует возвращение прежнего endpoint: такой результат
считается отказом восстановления. Этот адаптер не подключён к обновлению.

Дополнительно разрабатывается эксперимент `compose_nsfirewall_adapter.py`: он
закрепляет открытый дескриптор сетевого пространства Redis и устанавливает в нём
правило DROP, не отключая endpoint. Его граница доверия — root, kernel, локальный
Docker daemon и администраторы firewall; параллельные операции Docker, exec и
другие контроллеры запрещены. Проверки процессов и подключений дают состояние в
момент наблюдения и не заменяют постоянного контроля посторонних администраторов.
Необходима полная видимость host PID и `/proc`; её полнота является условием
окружения, а не доказанным свойством проверки. Контроллер проверяет отсутствие
чужих видимых потоков в закреплённом namespace, отклоняет ошибки чтения и ожидает
только штатные процессы init и Redis в контейнере.
Адаптер отказывает при непроверенном daemon, совпадении namespace с контроллером,
PID 1 или daemon, неожиданном процессе, capability, IPv6 и изменении правил.
Открытый namespace связан с PID Redis и PID daemon; соединение с daemon остаётся
открытым и проверяется вместе с Linux pidfd. `SO_PEERCRED` и отдельный вызов
`pidfd_open` не являются атомарным доказательством личности процесса: в окне
между ними остаётся риск повторного использования PID, в частности при передаче
сокета другому процессу. Условие безопасности — доверенный хост без передачи
сокета, перезапуска daemon и конкурентных действий администратора. Перезапуск
daemon или Redis во время операции не
поддерживается. До создания снимка ограниченный возврат Redis доступен новому
процессу при проверенном плане и checkpoint; оставшийся `operation.lock` этот
путь автоматически не удаляет. В исходном дереве также есть отдельные команды
снимка, возврата Redis, запуска прежних writers и финализации и экспериментальный
same-epoch `apply --fenced-update`. Для них требуется отдельно доверенный
подписанный исполнитель. Полный путь обновления, включая возврат после реального
сбоя и смену образов, ещё не подтверждён; перечисленные команды не входят в
опубликованный стабильный релиз и не являются инструкцией для действующей установки.
Старые версии `uterctl` не знают новых маркеров и не должны запускаться во время
экспериментальной операции, включая аварийное восстановление.

После усиления проверки личности Docker daemon [испытание на подписанном
Compose-комплекте](https://github.com/prince174/uter_deploy/actions/runs/41058508737)
остановилось до изменения firewall: Unix socket вернул PID 1 как peer, поэтому
адаптер не смог подтвердить, что подключён к проверенному dockerd. Этот результат
не означает, что усиленная версия прошла на опубликованной установке.
На [отдельном CI](https://github.com/prince174/uter_deploy/actions/runs/41059430725)
проверена атрибуция systemd socket activation в конкретный момент времени. Этот
исследовательский вариант добавлен в адаптер при условиях доверенного хоста,
полной видимости процессов и отсутствия конкурирующей передачи socket; он не
является независимой защитой от привилегированного вмешательства.
После добавления проверки systemd [повторный эксперимент с подписанным
Compose-комплектом 0.1.6](https://github.com/prince174/uter_deploy/actions/runs/41059705181)
прошёл: проверены изоляция в двух раундах, возврат Redis до снимка, создание
зашифрованного RDB-компонента и отказ автоматического возврата после снимка.
Очистка после снимка была выполнена отдельным кодом только в одноразовом CI;
это не реализация аварийного восстановления или обновления для пользователя.

[Следующее испытание Compose](https://github.com/prince174/uter_deploy/actions/runs/41062098065)
проверило SIGKILL контроллера до начала снимка и возврат Redis другим процессом
по аутентифицированному checkpoint. Тест также проверил сохранение записи и
endpoint и то, что writers остаются остановленными до отдельного возврата в CI.
Устаревшую блокировку в этом испытании удалял только родитель, который сам
завершил и дождался своего процесса. Такого автоматического удаления для обычной
установки не реализовано. Возврат после начала снимка этим путём запрещён.

[Kubernetes-этап finalizer](kubernetes-finalizer-primitive.md) проверен с
реальным kubectl на [одноразовом kind](https://github.com/prince174/uter_deploy/actions/runs/41051692689).
Этап не изолирует запись и не подтверждает принадлежность Pod подписанному
выпуску. При неизвестном результате API журнал сохраняется для разбора.

На [подписанном Kubernetes-комплекте 0.1.6 в одноразовом CI](https://github.com/prince174/uter_deploy/actions/runs/41057608156)
дополнительно проверены остановка тестовых writers, закрытие старого TCP-соединения
после перезапуска Redis с loopback bind, сохранение синтетического ключа,
зашифрованный RDB-компонент и тестовый возврат исходной конфигурации. Отдельно
проверены блокировка небезопасного перехода на 0.1.7 и восстановление копии в
другом namespace. Внешняя проверка допускает timeout и не доказывает причину
недоступности; устойчивость AOF на произвольном хранилище, изоляция всех внешних
writers и восстановление после аварии этими сценариями не доказаны. Успешного
обновления или переноса истории на 0.1.7 в этом испытании не было.

[Повторный Kubernetes CI](https://github.com/prince174/uter_deploy/actions/runs/41061924026)
дополнительно сохранил намерение с UID, resourceVersion и хешами Deployment до
изменения, искусственно вызвал ошибку после успешного PATCH и определил итоговое
состояние без повторной отправки PATCH. Ошибка вводилась после подтверждённого
ответа API, а не реальным сетевым обрывом. Запись намерения и классификация не
подтверждают изоляцию всех writers и не реализуют восстановление установки.

Экспериментальный Kubernetes coordinator и стадии его восстановления пока не
подключены к `uterctl`. Возврат исходного Deployment Redis намеренно
заблокирован до подтверждения непрерывного исключения внешних writers: даже до
запуска приложений новая копия Redis может стать доступна по сети. После
отправки обратного PATCH нельзя автоматически накатывать старую копию поверх
возможных новых записей. Неизвестный результат PATCH или удаления finalizer
сохраняется для разбора и повторно не отправляется.

Проверка структуры зашифрованного audit-архива и его HMAC-защиты как части
backup-набора не подтверждает целостность цепочки событий аудита. Отдельный
экспериментальный fingerprint Redis также не сравнивает его с содержимым RDB и
не разрешает запуск writers. До проверенного сравнения данных, сетевого барьера
и recovery в изолированном CI этот путь не является поддерживаемым способом
обновления или восстановления.

В [изолированном Kubernetes CI 41085286246](https://github.com/prince174/uter_deploy/actions/runs/41085286246)
на коммите `067d280` установлена подписанная версия 0.1.6 и повторно проверены
блокировки перехода на 0.1.7, сохранение тестовых данных и TTL, проверка двух
резервных копий и восстановление одной копии в отдельном namespace. Успешного
обновления на 0.1.7 или переноса истории этот тест не выполнял.

В конце того же сценария обязателен экспериментальный этап: на одноразовом
runner создаются свой ключ и подписанный executor, тестовые pins берутся из
того же kind-кластера. Executor останавливает writers и переключает Redis на
loopback. После этого его процесс принудительно завершается `SIGKILL`; только
CI-родитель, дождавшийся завершения именно этого процесса и проверивший PID в
файле блокировки, удаляет тестовую устаревшую блокировку. Новый процесс заново
проверяет pins и подписи, создаёт зашифрованный backup-набор и проверяет его
receipt. Для runtime сверяется содержимое расшифрованного tar с предварительным
HMAC-планом, для RDB выполняется структурная проверка, для конфигурационных
объектов проверяются UID и resourceVersion, для audit — структура tar и
криптографическая защита backup-набора. Это не проверка HMAC-цепочки самого
аудита и не сравнение данных RDB со всеми данными Redis.

В логе job виден общий `SESSION_GATE_E2E_PASS`; отдельные сообщения дочернего
процесса не публикуются. Успех этого этапа следует из обязательных проверок
кода сценария, включая код завершения `SIGKILL` и результат проверки receipt;
в отдельном артефакте эти сообщения не записаны. Указанное в артефакте
восстановление writers относится к предшествующему сценарию заблокированного
обновления. Экспериментальный coordinator после снимка writers не возобновлял;
одноразовый namespace оставлен для удаления вместе с runner.

Pins и ключ executor в этом испытании не являются независимым доверием
оператора. Постоянная защита от внешних writers, надёжность AOF/CSI,
production-восстановление устаревшей блокировки, проверка конкретных данных
созданного RDB, восстановление coordinator и HMAC-цепочка аудита здесь не
доказаны. Поэтому этот результат не открывает обновление и не подключает
экспериментальные стадии к пользовательскому `uterctl`.

# Мастер установки и обновления Uter

Мастер объединяет получение и проверку подписанного комплекта, подготовку установки,
проверки и запуск. Для обновления он проверяет переход, показывает план и вызывает
инструмент из подписанного целевого комплекта с зашифрованной резервной копией.
Инструкция использует выпуск `deploy-2026.10.29-signed-3` / `0.1.6`. Перед
установкой проверьте его подпись и отпечаток издателя по независимому каналу.
Ранее опубликован
[кандидат signed-2](https://github.com/prince174/uter_deploy/releases/tag/deploy-2026.10.29-signed-2).
В [изолированном CI](https://github.com/prince174/uter_deploy/actions/runs/40911282844)
на Compose и Kubernetes проверены мастер установки кандидата `signed-2` и переход
`0.1.5 → 0.1.6` на этот кандидат,
зашифрованная резервная копия и восстановление, отказ при неверном отпечатке и
недопустимом переходе. Для установки использовалась HTTP-заглушка LLM, при
обновлении — изолированный Ollama с реальным выводом модели.

Установка `signed-2` с настоящими LiteLLM и CPU vLLM отдельно прошла в
[Kubernetes](https://github.com/prince174/uter_deploy/actions/runs/40912395581/job/123583550008): проверены авторизованный smoke мастера и запрос через Uter.
Compose-ветка этого прогона завершилась с ошибкой и не подтверждает такой сценарий.

Для `signed-3` / `0.1.6` изолированный CI подтвердил [мастер установки и обновления
`0.1.5 → 0.1.6`](https://github.com/prince174/uter_deploy/actions/runs/40915339418)
с backup и восстановлением и [обычную установку](https://github.com/prince174/uter_deploy/actions/runs/40915352711)
на Compose и Kubernetes. В первом прогоне установка использовала HTTP-заглушку,
а обновление — изолированный Ollama с реальным выводом модели.
В [отдельном прогоне](https://github.com/prince174/uter_deploy/actions/runs/40916765054)
обе установки мастером прошли с LiteLLM и CPU vLLM и небольшой тестовой моделью:
проверялись авторизованный smoke и запрос через Uter.

[Другой прогон](https://github.com/prince174/uter_deploy/actions/runs/40915346820)
прошёл на Kubernetes, но в Compose `/chat` вернул HTTP 504, а последующая проверка
показала неготовность upstream. Причина тайм-аута не установлена; успешный повтор
не гарантирует стабильность CPU vLLM, производительность или работу другой модели.

## 1. Подготовить инфраструктуру и доверие

Нужен Linux amd64 с Python 3.11+, модулем `venv`, pip, Git и доступом к доверенному
источнику Python-зависимостей и публичному GHCR. Для Compose необходимы Docker и
Compose версии не ниже 2.30, локальный Unix socket и права запуска команд Docker;
описанный ниже вариант использует root. Для Kubernetes нужны `kubectl`, Helm 3.17.3,
явный kube-context, рабочие PVC/StorageClass и права создавать ресурсы в новом
namespace. NetworkPolicy требует поддерживающего её CNI. Ingress, внешний TLS и
права на существующую инфраструктуру настраиваются отдельно.

LiteLLM и vLLM должны уже работать. Подготовьте OpenAI-совместимый base URL
LiteLLM, например `https://litellm.example.internal/v1`, опубликованный alias
модели, необходимый ключ и доступ к `/health`. Убедитесь, что LiteLLM достигает
vLLM, а будущие контейнер или Pod Uter могут достигать LiteLLM. Не подставляйте
в URL пароль или токен. Успешная проверка с хоста сама по себе не подтверждает
сеть и доверенные CA внутри контейнера или Pod. Модель должна быть полностью
загружена и отвечать на выбранный alias, а ресурсы LiteLLM/vLLM и задержки —
соответствовать ожидаемой нагрузке и тайм-аутам. Uter не управляет внешней LLM и
не гарантирует её стабильность: проверьте эти условия в своём окружении.

**Независимо получите и сверьте отпечаток публичного ключа издателя:**
`65be6fd9613fa7e879735fe5b453bfcb8c0e38911cd7429c9aac9c9afba676a2`.
Отпечаток из того же Git-репозитория, что и комплект, не устанавливает доверие к
издателю. Публичный ключ и этот отпечаток не являются резервным ключом или
паролем. Bootstrap запускается из доверенной копии Git: он не удостоверяет своё
собственное происхождение, операционную систему, Python, pip или индекс пакетов.
Docker и Compose, либо `kubectl` и Helm, а также каталоги из `PATH` тоже должны
быть доверенными и защищёнными от подмены; проверка bootstrap не подтверждает
подлинность этих системных исполняемых файлов. Доступ на запись к checkout,
Python-окружению и их родительским каталогам должен быть ограничен root или
оператором. Копия bootstrap включена в bundle, но сам bootstrap отказывает при
запуске из подписанного bundle: запускайте его из доверенного checkout и не
создавайте виртуальное окружение внутри bundle, чтобы сохранить проверку подписи.

Проверенные подписанные комплекты, установочный каталог, созданные учётные данные,
файл ключа LLM и резервные копии храните в защищённых каталогах. Пути и их предки
не должны быть ссылками или быть доступны на запись другим пользователям; файл
ключа LLM должен принадлежать запускающему пользователю и иметь права `0600`.
При `sudo` подготовьте доступные root защищённые пути. Сам ключ не передавайте
через аргументы командной строки, переменные окружения, логи или чат.

## 2. Запустить мастер для Compose

Создайте **новую** root-owned копию и новый приватный
каталог для выпусков. Пример использует новые пути `/srv/uter-deploy-tooling` и
`/srv/uter-wizard-private`; при их существовании выберите другие, не удаляя данные:

```bash
sudo git clone --branch deploy-2026.10.29-signed-3 --single-branch \
  https://github.com/prince174/uter_deploy.git /srv/uter-deploy-tooling
sudo mkdir -m 700 /srv/uter-wizard-private
cd /srv/uter-deploy-tooling
sudo python3 -I scripts/bootstrap_wizard.py install \
  --backend compose --name uter-instance \
  --home /srv/uter-instance --release-dir /srv/uter-wizard-private/release-016
```

`-I` отключает пользовательские пути импорта Python; это не подтверждает подлинность
самого Python, checkout или источника пакетов. Если модуль создания окружения или
pip не установлен, установите его штатным способом для выбранной версии Python.
Bootstrap создаст защищённое окружение в checkout, установит зависимости и
запустит мастер. Не изменяйте подписанный bundle или проверенные скрипты.

В интерактивных подсказках подтвердите тег и версию, введите независимо проверенный
SHA-256 издателя и параметры LiteLLM. Для ключа выберите `файл` (`file`),
`ввести` (`enter`) для скрытого ввода или `нет` (`none`), если ключ не требуется;
скрытый ввод требует работающего терминала. На вопросы о разрешении HTTP и
пропуске проверки LLM с хоста ответ `да` или `yes` включает соответствующую
опцию; другой ответ её не включает.
Задайте свободный локальный порт и, при необходимости, путь полного CA-bundle.
Мастер загрузит выпуск, проверит ключ, подпись и хеш входных данных, выполнит
проверку хоста и LLM, `prepare`, `check`, `install` и авторизованный smoke-тест.
Сообщение об успехе относится к выполненным проверкам; проверьте свои реальные
запросы и организуйте TLS reverse proxy до внешнего доступа.

Мастер можно запустить без указания действия и выбрать его в меню:

```bash
sudo python3 -I scripts/bootstrap_wizard.py
```

Он создаёт отдельную установку; существующие каталоги и ресурсы не перезаписываются.
При прерванной установке не удаляйте данные и не обходите состояние `pending`:
сначала выполните диагностику по [README](../README.md) и разберите владение ресурсами.

## 3. Запустить мастер для Kubernetes

Используйте защищённый checkout пользователя, который имеет права в **нужном**
кластере. Укажите явно выбранный kube-context; пример предполагает, что имена
каталогов ещё свободны. Приведённый namespace будет равен `--name`:

```bash
mkdir -m 700 "$HOME/uter-wizard-private"
git clone --branch deploy-2026.10.29-signed-3 --single-branch \
  https://github.com/prince174/uter_deploy.git "$HOME/uter-deploy-tooling"
kubectl config get-contexts
CONTEXT='укажите-имя-контекста'
python3 -I "$HOME/uter-deploy-tooling/scripts/bootstrap_wizard.py" install \
  --backend kubernetes --name uter-instance --context "$CONTEXT" \
  --home "$HOME/uter-wizard-private/installation" \
  --release-dir "$HOME/uter-wizard-private/release-016"
```

При необходимости отдельно укажите `--storage-class`. Успех мастера включает
временный собственный `kubectl port-forward` и авторизованный smoke-тест, но не
означает, что настроены корпоративные DNS, Ingress, TLS, внешние сетевые политики,
резервное копирование внешних систем или отказоустойчивость. Предварительно
проверьте права, квоты, PV и доступность registry на узлах. Сгенерированный
`resources.yaml` содержит секреты открытым текстом; Kubernetes Secret сам по себе
не гарантирует шифрование в хранилище кластера.

## 4. Специальные варианты установки

Для корпоративного CA укажите `--llm-ca-bundle /path/to/complete-ca-bundle.pem`.
Он задаёт **полный** доверенный PEM-набор для процесса Guardrail и не добавляется
автоматически к стандартному набору. Проверьте полную цепочку и имя сертификата.
Клиентские сертификаты mTLS мастер не настраивает.

`--skip-llm-preflight` пропускает только проверку LLM с хоста: например, если DNS
LiteLLM существует только внутри кластера. Проверки инструментов и выбранного
контекста остаются обязательными, как и итоговый smoke через Uter. Результат не
подтверждает доступ к LLM из других сетей. Для HTTP необходим явный
`--allow-http-llm`; используйте его только в доверенной тестовой сети. Прокси из
переменных окружения применяется к проверке хоста только при `--use-env-proxy`.

Для предварительно проверенного локального выпуска `--reuse-release` использует
существующий защищённый `--release-dir`, повторно проверяя подпись и хеши.
`--offline` поддерживается только для Compose и запрещает загрузку образов при
установке; точные подписанные digest должны заранее присутствовать в локальном
daemon. Чтобы избежать **также загрузки релиза**, сочетайте его с `--reuse-release`.
LLM и другие зависимости всё равно могут требовать сеть. Kubernetes offline-режим
не поддерживается. Перенос образов с сохранением нужных ссылок проверьте заранее.

Для автоматизации можно передать параметры без интерактивных вопросов через
`install --non-interactive`; ключ при этом передаётся только через защищённый
`--llm-key-file PATH`. Доступные параметры показаны после создания окружения:

```bash
/path/to/private-venv/bin/python -I /path/to/trusted-checkout/scripts/install_wizard.py --help
```

## Диагностика установки

При ошибке мастера сохраните защищённый каталог установки и запишите название
последнего этапа и фиксированный код, например `ACCEPTANCE_FAILED` и, если он
выведен, `ACCEPTANCE_DIAGNOSTIC=CHAT_HTTP_504`. Диагностика использует только
фиксированные категории и не включает тело ответа, URL или токен. Код определяет
этап и наблюдение, но сам по себе не устанавливает первопричину:

| Этап | Что проверить |
|---|---|
| `READY` | Доступность Uter на локальном порту, готовность контейнеров или Pod, свободный порт и состояние хранилища. |
| `AUTH` | Созданные учётные данные, возможность входа и время на хосте; значения паролей не выводите. |
| `HEALTH` / `NOT_READY` | Доступность upstream, Agent и toxicity-модели; отдельно проверьте DNS, TLS и сеть из контейнера или Pod. |
| `CHAT` / `HTTP_504` или `TIMEOUT` | Готовность модели и alias, прямой тест LiteLLM, связь LiteLLM → vLLM, ресурсы и время генерации. HTTP 504 указывает на тайм-аут, но не определяет, какой компонент стал его причиной. |

Для диагностики используйте состояние сервисов и руководство
[«Если что-то не работает»](corporate-litellm-deployment.md#если-что-то-не-работает).
Просмотрите подробные журналы только в доверенном окружении: они могут содержать
запросы или секреты. При обращении за помощью передавайте фиксированный код,
название этапа и версию; пароли, токены, содержимое `credentials.json`, ключи,
тела запросов и ответов и сырые логи не отправляйте. При неудачной проверке не
удаляйте состояние или тома и не запускайте повторную установку поверх существующей;
дальнейшие действия зависят от статуса установки и описаны в
[разделе об ошибках и восстановлении](../README.md#ошибки-повторный-запуск-и-обновление).

## 5. Обновить существующую установку

В подписанном манифесте `0.1.6` указаны `data_epoch = 1` и переход **только с `0.1.5`**. В проверенных
`0.1.5` и `signed-2` одинаковые образы Uter: такой переход не доказывает миграцию данных между
разными сборками продукта или совместимость произвольных данных. Сверьте эту
декларацию в проверенных подписанных комплектах перед обновлением. `signed-2`
и `signed-3` имеют одну версию `0.1.6`; переход `0.1.6 → 0.1.6` не заявлен.

Согласуйте окно обслуживания, проверьте свободное место и остановите внешние записи
непосредственно в Redis и том аудита. Инструмент временно остановит компоненты Uter.
Сохраните подписанный комплект текущей версии: при первом принятии установки под
управление он обязателен. Мастер не заменяет существующий ключ резервной копии.

Из доверенного checkout запустите мастер `update`, например для Compose:

```bash
sudo python3 -I /srv/uter-deploy-tooling/scripts/bootstrap_wizard.py update \
  --home /srv/uter-instance \
  --release deploy-2026.10.29-signed-3 --version 0.1.6 \
  --download-to /srv/uter-wizard-private/release-016-update \
  --fingerprint "$UTER_PUBLISHER_SHA256" \
  --current-bundle /srv/uter-wizard-private/release-015/bundle \
  --backup-root /srv/uter-wizard-private/backups \
  --backup-key /srv/uter-wizard-private/backup-key/backup.key
```

Перед запуском задайте `UTER_PUBLISHER_SHA256` **независимо полученным и сверенным**
отпечатком публичного ключа, а пути замените на свои. `release-016-update` должен
быть новым каталогом с защищённым родителем. В нём мастер сохранит скачанный и
проверенный выпуск; `release-015/bundle` — заранее полученный и проверенный текущий
комплект. Для ранее принятой под управление установки `--current-bundle` можно
не указывать: мастер проверит сохранённый текущий комплект. Если указать
`--check-only`, установка не меняется, однако вариант `--release` всё равно скачает
выпуск в новый каталог. Для проверки без скачивания используйте `--bundle PATH`
и `--publisher-key PATH` вместо `--release`, `--version` и `--download-to`.

Просмотрите план: версия, backend, context, путь копии и путь к ключу. Для
интерактивного запуска подтвердите действие словом `UPDATE`; `--confirm` является
явным подтверждением в автоматизированном сценарии. Мастер проверяет подписи и
совместимость, создаёт или использует защищённый ключ, делает зашифрованную копию,
обновляет компоненты и выполняет проверку. Для существующего ключа новый не создаётся.
`--offline` в обновлении запрещает загрузку образов только для Compose; локальные
точные образы обеих версий нужны заранее, а `--release` всё равно загружает комплект.

Копию и ключ сохраните раздельно вне сервера и регулярно проверяйте восстановление.
Без ключа копию не восстановить. Внешние LiteLLM/vLLM, их модели и данные,
Ingress, DNS и сторонние секреты этим инструментом не резервируются. Снимок Redis
ограничен 100 МиБ. После пересоздания ресурсов привязка планового резервирования
может потребовать явной повторной регистрации; см. [плановые копии](scheduled-backup.md).

При ошибке сохраняйте каталоги и журналы и используйте
[процедуру восстановления](managed-update-recovery.md). Восстановление создаёт
новый проект или namespace и не переключает трафик самостоятельно; автоматический
откат всех данных и внешних систем не обещается.

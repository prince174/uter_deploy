# Защитный барьер для истории сессий

В старой версии пользовательские идентификаторы могли использоваться как alias
при записи истории. Новая версия применяет другую привязку. По имени ключа Redis
нельзя надёжно установить владельца каждой старой истории; автоматическое
объединение или перенос таких данных может раскрыть историю другому пользователю.

Подписанный переход с `data_epoch=1` на `data_epoch=2` с политикой
`block_unverified_sessions` выполняется только новым инструментом из проверенного
комплекта. Старый контроллер отказывает из-за изменения epoch. Непосредственно перед
проверкой инструмент создаёт зашифрованную резервную копию и останавливает писателей
Uter. Наличие любого неистёкшего ключа `sess:*` в любой проверенной базе Redis
рассматривается как неоднозначность: это консервативная политика, поскольку
надёжного реестра владельцев ключей нет. Имена и содержимое сессий не выводятся.

При неоднозначных сессиях или ошибке проверки старая версия возобновляется,
а новая не применяется. Результат указывает причину и путь к резервной копии.
Проверка целостности копии и пробное восстановление — разные операции. Redis RDB
сохраняет абсолютные сроки истечения ключей: после истечения срока восстановление
самого RDB не гарантирует, что истёкшая сессия вновь будет доступна. Для длительного
сохранения требуется отдельный согласованный способ архивирования истории.

В [изолированном CI](https://github.com/prince174/uter_deploy/actions/runs/41024366249)
для Compose и Kubernetes проверены отказ при тестовой неоднозначной сессии,
возобновление старой версии, криптографическая проверка копии и пробное
восстановление тестовой сессии и HMAC-аудита. Старый контроллер отказал переходу
между epoch; при пустой тестовой базе без доказанного fence новый контроллер тоже
отказал. Проверка охватывает синтетические данные и не доказывает бессрочное
хранение или отсутствие внешних писателей в другой инфраструктуре.

**Пока нет проверенного механизма блокировки внешних писателей Redis**, этот переход
останавливается и при отсутствии `sess:*` с кодом `SESSION_MIGRATION_FENCE_UNVERIFIED`.
Пустой результат сканирования сам по себе не гарантирует, что новая запись не
появится до переключения версий. Это ограничение: процедура пока не разрешает
успешное обновление с epoch 1 на epoch 2. `--check-only` не выполняет проверку
работающего Redis и не подтверждает возможность обновления.

Если был создан `session-migration-block.json`, не удаляйте отчёт и не запускайте
обновление повторно до проверки состояния установки и сохранённой копии. Если
возобновление старых компонентов завершилось ошибкой, сохранён журнал операции;
сначала восстановите доступность старой версии по документации восстановления.

Предварительный выпуск `deploy-2026.10.30-test-1` отозван: его подписанный архив
был удалён из публикации, но ранее скачанные копии отозвать нельзя. Не используйте
его для обновления. Стабильный выпуск остаётся `0.1.6`.

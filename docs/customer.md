# Установка и обновление у заказчика

## Граница первого профиля

Linux amd64, Python 3.12 для контроллера, Docker Compose >=2.30 либо Helm 3.17.3
и Kubernetes >=1.27. Поддержка конкретной версии Kubernetes требует теста в контуре.
Один экземпляр каждого сервиса; при обновлении возможен простой. Доступ снаружи —
через TLS reverse proxy/Ingress заказчика. В Compose порт Guardrail привязан к localhost;
в Helm только ClusterIP. Не открывайте Agent и Redis наружу.
NetworkPolicy ограничивает ingress при наличии поддерживающего CNI. Egress,
внутрикластерный TLS и внешние CA настраиваются инфраструктурой заказчика.

## Постоянный каталог

```
/srv/uter/
  customer/
    site.json
    guardrail.env
    agent.env
    redis.conf
    redis-password
    audit-hmac-key
    policies/customer.toml
    profiles/model_profiles.toml
    models/
    acceptance.py
    values.yaml                 # для Helm вместо Compose env-файлов
  releases/                     # проверенные неизменяемые комплекты
  state.json                    # current / previous / pending
```

Скопируйте примеры в `customer/` один раз и заполните. Контроллер их не переписывает.
`site.json` определяет backend, постоянное имя установки и namespace. Не меняйте их
между обновлениями: иначе получите другую установку и другие тома. Имя не должно
совпадать с существующим стендом разработчика.

Пароли для ADMIN/USER/SERVICE в guardrail задаются bcrypt-хешами; агенту нужен
соответствующий SERVICE plaintext password. Shared secret в обоих сервисах совпадает.
В raw env_file не заключайте значения в кавычки: кавычки станут частью значения.
Redis password в `redis.conf` и `redis-password` должен совпадать.
Файлы секретов: владельцы/права должны разрешать чтение только администратору
и нужному UID контейнера. Не печатайте развёрнутый `compose config` с реальными env.
Секреты приложения доступны администратору Docker/Kubernetes — это не защита от root.

Политики, профили и модели выдаются как отдельно согласованные runtime-ресурсы.
Не копируйте весь каталог разработки. Пути моделей в политике должны указывать
на `/app/models/...`; toxicity-модель должна быть предзагружена в runtime image.
Изменение моделей/политик тестируется отдельно, контроллер их не заменяет автоматически.
Для RAG настройте реальные интеграции: продукт содержит встроенные демонстрационные
registry, поэтому готовность HTTP сама по себе не подтверждает реальные данные.

## Helm

Создайте ресурсы из `examples/values.yaml` в целевом namespace:

- `guardrailSecret`: env-ключи из guardrail.env плюс `AUDIT_LOG_HMAC_KEY`.
- `agentSecret`: env-ключи из agent.env.
- `redisSecret`: ключ `password`.
- `policyConfigMap`: ключ `customer.toml`.
- `profileConfigMap`: ключ `model_profiles.toml`.
- `modelsClaim`: подготовленный PVC с моделями.

Скопируйте `examples/values.yaml` в `customer/values.yaml`, заполните endpoint LLM.
Для private registry добавьте `imagePullSecrets`. Выдайте оператору необходимые RBAC.
Контроллер не читает Secret из кластера; существование и содержимое проверяются при
установке/acceptance. Кастомные Env не должны дублировать фиксированные служебные ключи.
PVC аудита и Redis помечены keep; uninstall не является удалением данных.

## Проверка и применение

Установите контроллер и зависимости из доверенного релиза tooling. Публичный Ed25519
ключ издателя получите независимо от скачанного комплекта. `verify` проверяет именно
этот ключ. Доверие ключу не устанавливается автоматически.

Выполните команды из README. Для существующей установки требуется receipt:

```json
{"version":"1.0.0","backup_id":"storage-snapshot-2026-10-22-001"}
```

Это подтверждение оператора, а не автоматическая проверка резервной копии.
Перед его созданием сохраните согласованные снимки Redis, аудита, индексов RAG,
конфигурации и ключей; проверьте процедуру восстановления. Внешние системы требуют
своих backup-процедур. Контроллер не создаёт backup и не запускает миграции данных.

`acceptance.py` — тест заказчика с ненулевым exit code на ошибке. Обязательные сценарии:
авторизация, обычный запрос, блокировка опасного запроса, сохранение аудита и реальные
источники RAG (если используются). Его путь/аргументы находятся в `smoke_command`.
Это доверенная команда заказчика, выполняемая на машине оператора без shell.

## Сбой и откат

`pending` означает, что часть сервисов уже могла измениться. Сначала изучите состояние.
Исправив причину, повторите ту же версию через `resume --bundle ...` с новым receipt
на pending-версию. Либо выполните `rollback`: при незавершённом обновлении он возвращает
последний успешный комплект; после успешного — предыдущий. Данные не восстанавливаются
автоматически. Смена data_epoch запрещена до отдельной процедуры миграции.

При сбое самой первой установки предыдущего комплекта нет: используется `resume`.
После аварийного завершения процесса может остаться operation.lock. Удалять его можно
только убедившись, что другой uterctl не работает. Не удаляйте state.json ради обхода проверок.

## Закрытый контур

Перенесите проверенный комплект, образы и модели разрешённым каналом. Образы импортируйте
во внутренний registry с сохранением manifest digest или заранее загрузите на нужные
узлы. Если меняется адрес registry, поставщик должен выпустить и подписать соответствующий
manifest. Не редактируйте подписанные файлы. Для Compose `--offline` запрещает pull;
нужные digest references должны уже разрешаться локально (проверить до окна обновления).
Для Kubernetes заранее обеспечьте доступ к внутреннему registry или кеши всех узлов;
флаг offline не управляет сетевой политикой kubelet. HF offline включён только у Guardrail;
модели внешних систем и embeddings надо подготовить отдельно.

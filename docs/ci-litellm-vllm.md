# Изолированная проверка LiteLLM и CPU vLLM

Workflow `Verify Uter with LiteLLM and CPU vLLM` рассчитан только на временный
GitHub-hosted Linux runner. Matrix создаёт две независимые установки: Compose и
отдельный kind-кластер с собственным namespace. Он скачивает публичный выпуск,
сверяет отпечаток ключа, проверяет подписанный комплект и извлекает установочный
архив через проверку его подписанного хеша. Требуется выпуск, подписывающий
`installation_archive_sha256`; версия задаётся при запуске workflow.

Проверка запускает отдельно LiteLLM и CPU vLLM, получает реальные ответы напрямую
от обоих серверов и затем через Uter. Для последнего запроса дополнительно
проверяется рост счётчика сгенерированных токенов vLLM. Для короткой проверки
каждый запрос ограничен четырьмя выходными токенами, тайм-аут запроса — 360 секунд.
Этапы ожидания моделей и запросов vLLM, LiteLLM и Uter логируются отдельно без
текста ответов; категории тайм-аутов различаются по этапам. В CPU CI используется
`--enforce-eager`: для закреплённого vLLM 0.32 он выключает `torch.compile`, а при
явном размере кеша пропускает предварительный прогрев. Это настройка теста, не
оценка производительности и не обещание более быстрого ответа на любом CPU. Модель
`HuggingFaceTB/SmolLM2-135M-Instruct` закреплена по revision
`a5cf62c9a838db1be8f34394f02edb89f718a9ed`, образы — по digest. Сценарий со SmolLM2 успешно прошёл обе платформы в одном CI-прогоне. Открытая модель
служит только для проверки интеграции, а не оценки качества модели или
готовности окружения к рабочей нагрузке.

Runner скачает CPU-образ vLLM приблизительно на 1,72 ГБ и веса модели примерно на
0,269 ГБ; дополнительно скачиваются LiteLLM, образы Uter и kind для Kubernetes.
Распакованные файлы занимают больше места. Перед загрузкой драйвер проверяет
поддержку AVX2 или AVX512, доступную RAM и свободное место в каталоге задания
и `/var/lib/docker`: минимум 12 ГиБ доступной RAM для обоих вариантов и
свободного диска не менее 8 ГиБ для Compose или 10 ГиБ для Kubernetes. Порог RAM
учитывает лимит контейнера vLLM 9 ГиБ и первоначальный запас 3 ГиБ для хоста и
остальных компонентов. Совпадающий лимит memory-swap 9 ГиБ не позволяет vLLM
использовать swap. Эти значения не резервируют память; суммарные лимиты vLLM,
LiteLLM и kind/Uter больше RAM стандартного 16-ГБ runner. Это предварительный
отсев, а не гарантия, что все образы поместятся или что вычислительных ресурсов
хватит для запуска. Контейнеры и kind ограничены по CPU
и памяти; результаты зависят от ресурсов конкретного runner. Для CI-модели
0,135B задаётся KV cache 256 МиБ (`--kv-cache-memory-bytes 268435456`) и не более
одного одновременного запроса. Старую переменную `VLLM_CPU_KVCACHE_SPACE` в
контейнер не передают: в vLLM 0.32 любое непустое значение, включая `0`,
переопределяет аргумент, а пустая строка не является числом. Закреплённый
образ не задаёт эту переменную.
Это узкая тестовая настройка, не рекомендация для других моделей, длины контекста,
параллельных запросов или рабочих нагрузок: при недостаточном размере кеша сервер
откажет в запуске или обслуживании запроса.

Ключ LiteLLM генерируется отдельно для каждого задания. vLLM доступен для теста
на localhost и внутри временной сети Docker; LiteLLM привязывается к приватному
адресу Docker gateway соответствующего backend и требует ключ. Это ограничение
привязки не заменяет сетевую политику и не следует переносить как готовую
конфигурацию для рабочего окружения. Ключи, содержимое ответов и подробные логи
не публикуются. Ошибки выводятся категориями; при сбое установки Kubernetes до
удаления кластера дополнительно выводятся только разрешённые категории состояний
Pod/PVC, контейнеров, Warning events и Helm. Подтверждённый текстом Helm timeout
отмечается отдельно; без такого подтверждения его причина остаётся неизвестной.
Имена объектов, тексты сообщений, переменные окружения и stderr не выводятся.
При завершении задание удаляет созданные им временные контейнеры и kind-кластер.

Этот workflow проверяет только изолированный CI и не доказывает совместимость
чужих GPU-драйверов, TLS, ограничений Kubernetes NetworkPolicy, внешних LLM,
нагрузки или производительности. GPU-вариант vLLM им не проверяется.

## Проверенный результат

Для публичного выпуска `0.1.4` полная цепочка Uter → LiteLLM → vLLM прошла
на Compose в [прогоне 40670394457](https://github.com/prince174/uter_deploy/actions/runs/40670394457)
и на Kubernetes в [прогоне 40672187144](https://github.com/prince174/uter_deploy/actions/runs/40672187144).
В каждом успешном задании проверены прямой ответ vLLM, ответ через LiteLLM, запрос
через Uter и рост счётчика генерации vLLM. В этих прогонах использовалась модель
`Qwen/Qwen2.5-0.5B-Instruct` с revision `2b01de6d1108f9b2b5e46a726aa678a359b6c03b`;
реальные ответы и секреты не публиковались.

С меньшей моделью `HuggingFaceTB/SmolLM2-135M-Instruct` обе платформы успешно
прошли в одном [прогоне 40674274046](https://github.com/prince174/uter_deploy/actions/runs/40674274046):
проверены оба прямых ответа, ответ Uter и рост счётчика генерации vLLM. Это один
успешный прогон, а не доказательство стабильности под нагрузкой или на всех CPU.

**История проверок Qwen:** в первом прогоне Kubernetes не завершил
установку Uter, а в повторном прогоне она не завершилась для Compose. В каждом из
этих случаев два LLM-сервиса ответили напрямую; причина ошибки установки не установлена.
Оба прогона matrix в целом завершились с ошибкой, поскольку в каждом одна из двух
платформ не прошла. Успехи относятся к отдельным заданиям, а не к полностью зелёному
matrix. Эти результаты не доказывают стабильность на разных машинах или под нагрузкой.

Окружения и LLM-сервисы создавались только на отдельных временных GitHub-hosted runner
и удалялись после теста. На отдельном пользовательском сервере сценарий пока не
проверялся; запущенного постоянного экземпляра LiteLLM/vLLM эта проверка не оставляет.

## 1. Проверка всех слоёв

673e807: scan_image_archive проверяет каждый слой, включая удалённые позже файлы.
Запрет собственного Python-кода вне разрешённых каталогов зависимостей, .git/.env,
типовых credential-файлов, debug-файлов; проверка credential-подобных Env и маркера
private key в image config/history. Отчёт не содержит значений секретов.
Дополнительно сравниваются SHA-256 всех собственных .py исходного snapshot, независимо
от расширения файла внутри образа. Это ловит переименованные точные копии, но не
доказывает отсутствие преобразованного кода в сторонней библиотеке.

ZIP/WHL/EGG/PYZ и TAR/TGZ по расширению проверяются рекурсивно (до 3 уровней,
64 MiB упакованного / 256 MiB распакованного содержимого на архив). Превышение лимита,
повреждённый или зашифрованный архив блокируют проверку. Произвольные архивы без
распознаваемого расширения и сериализованные веса моделей этим правилом не покрываются.
Разрешён Python stdlib/site-packages и узкие системные каталоги libstdcxx/gdb;
вложенный ensurepip wheel разрешён отдельно. Собственные хеши проверяются и в исключениях.
Это не полный DLP/secret scanner, а отдельный барьер против утечки исходников.

Исходные сохранённые hardened-образы от 22.10: Agent 9 слоёв / 11271 файл;
Guardrail 10 слоёв / 35828 файлов. 66 уникальных SHA-256 собственных .py;
запрещённых файлов/точных копий не найдено. Отчёты локально work/full-*-scan.json.

## 3. Отладочные данные и docstrings

Исходные 21/38 ELF-модуля уже не содержали .debug*, .zdebug* и .symtab.
2a48317: явный strip --strip-debug и --python-flag=no_docstrings при компиляции.
Это убирает документационные строки собственных модулей; нужные exports/метаданные
и строки бизнес-логики не вырезаются. OpenAPI и runtime проверяются после компиляции.
Рекомендуемые инструменты описаны в [Nuitka manual](https://nuitka.net/user-documentation/user-manual.html)
и [GNU strip](https://www.sourceware.org/binutils/docs/binutils/strip.html).

## 4. Ограниченная оценка реверса

12f71bc: audit_binary_exposure разбирает ELF section tables и ищет исходные строковые
литералы (24–4096 символов), не исполняя извлечённый код. В отчёте только счётчики,
имена модулей и SHA-256, без самих промптов/строк. Для baseline использованы исходники
как эталон (source-assisted), поэтому это не слепая атака и не измерение времени реверса.
Из 1074 уникальных эталонных литералов найдено 251 совпадение по модулям Agent и 821
по модулям Guardrail. Суммы включают повторения между модулями; 0 совпадений тоже
не означало бы невозможность извлечения строк другим методом.

Runtime harness пытается inspect.getsource для собственных callable-объектов и
блокирует проверку, если получает исходник. Отдельно считает доступные docstrings и
непустые co_code; наличие этих байтов само по себе не означает восстановимый Python
алгоритм (возможны синтетические code objects). Дополнительная runtime-проверка (428f3e5) пытается получить PII_PATTERNS из
скомпилированного OutputGuard и повторно применить email-правило к синтетической
строке. Сохраняются число правил, хеш таблицы и результат, без самих выражений.
Для этого runtime-теста исходники в контейнер не монтируются. Это не полноценная декомпиляция,
не восстановление алгоритмов и не оценка специалистом по реверс-инжинирингу.

## 5. Решение о дополнительной обфускации

Базовое усиление оправдано для развёртывания без передачи исходных файлов. Защита строк
требует отдельной проверки: дополнительный модуль защиты Nuitka не включён, неизвестный
обфускатор в сборку не добавлен. Измеримый остаточный риск — доступные тексты/метаданные
и возможность runtime-анализа у root. Для следующего этапа нужны выбранные критичные
модули и критерий проверки извлечения; шифрование с ключом в том же контейнере
не является гарантией против администратора хоста. Политики и модели остаются доступны.
Конфиденциальность от root потребовала бы иной модели развёртывания (внешний доверенный
сервис либо корректно аттестуемая TEE), сейчас это не реализуется.

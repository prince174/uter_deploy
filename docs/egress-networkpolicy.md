# Ограничение исходящих соединений Kubernetes

Это дополнительный профиль для Kubernetes с CNI, который обеспечивает соблюдение
`networking.k8s.io/NetworkPolicy`. По умолчанию профиль выключен: при обычной
установке исходящий трафик Uter этими правилами не ограничен. Настраивайте профиль
совместно с администратором сети и сначала проверяйте в отдельном окружении.

## Что нужно до включения

1. Выберите точные адресаты DNS и LiteLLM, их порты и способ доступа из Pod Uter.
   Для сервисов внутри кластера узнайте namespace и метку именно Pod, а не только
   метку Service. Для внешнего endpoint можно задать один стабильный IPv4-адрес.
2. Убедитесь, что CNI поддерживает NetworkPolicy. При NodeLocal DNSCache, другом
   DNS endpoint, нестандартном порте, NAT или Service с внешними адресами правила
   зависят от реализации сети; проверьте их в конкретном кластере. Селектор Pod
   обычного CoreDNS в примере ниже может не подходить вашей установке.
3. Выделите окно без параллельного обновления, восстановления и резервного
   копирования. Настройка сетевой политики может сделать сервис недоступным.
4. Профиль разрешает Guardrail соединения к Agent:8001, Redis:6379 и выбранному
   LiteLLM, Agent — к Guardrail:8000, Guardrail и Agent — к выбранному DNS по UDP
   и TCP. Redis получает пустой список разрешённых исходящих соединений.
   Ответы на разрешённые соединения учитываются сетевой политикой как ответный
   трафик. Отдельный judge, внешние инструменты Agent, другие endpoints, IPv6 и
   несколько внешних IP этот профиль не разрешает. Если они нужны, профиль в
   таком виде применять нельзя без согласованных дополнительных политик.

Kubernetes объединяет разрешения всех NetworkPolicy, применимых к Pod. Другая
широкая разрешающая политика может открыть дополнительные направления; CNI,
политики уровня кластера, hostNetwork и трафик к узлам имеют собственные
особенности. Селекторы защищают только при контроле прав на изменение меток и
создание Pod в выбранном namespace. IP-правило разрешает указанный IP и порт,
а не только одно имя или приложение. Используйте отдельные сетевые ограничения
и проверяйте фактический трафик в своей сети.

В стандартной NetworkPolicy нет выбора внешнего получателя по FQDN. Автоматическое
преобразование имени LiteLLM в IP при установке не выполняется: DNS может вернуть
несколько адресов или измениться позже. Для динамического FQDN используйте
корпоративный egress proxy/gateway или возможности конкретного CNI, согласованные
с сетевой командой. Настройка TLS и доверенного CA остаётся обязательной там, где
она требуется; NetworkPolicy не заменяет проверку TLS.

## Включение до первой установки

После `install.py prepare` и **до** `install.py check` и `install.py install`
откройте `<home>/values.yaml` и добавьте блок, заменив значения на действительные
для своего кластера. Ключи, пароли и содержимое Kubernetes Secret в этот файл не
добавляйте.

```yaml
networkPolicy:
  egress:
    enabled: true
    dns:
      mode: pod
      namespace: kube-system
      podLabelKey: k8s-app
      podLabelValue: kube-dns
      port: 53
    llm:
      mode: pod
      namespace: litellm-namespace
      podLabelKey: app
      podLabelValue: litellm
      port: 8080
```

`namespace` — точное имя namespace, `podLabelKey` — простой ключ метки без
префикса, `podLabelValue` — непустое значение. Убедитесь, что оба селектора
выбирают нужные Pod и только их. Для DNS или LiteLLM с одним внешним стабильным
IPv4 вместо соответствующего блока `mode: pod` можно задать:

```yaml
mode: ipv4
ipv4: '192.0.2.8'  # пример: заменить реальным адресом
port: 443           # заменить реальным портом
```

Chart формирует для него `/32`; CIDR, IPv6 и FQDN в `ipv4` не принимаются. DNS
обычно использует порт 53; LiteLLM — порт своего endpoint. DNS и LiteLLM можно
настроить разными способами. Убедитесь, что URL LLM и разрешённый адресат
действительно соответствуют друг другу: chart не сопоставляет их автоматически.
При включении неполные или некорректные параметры приводят к ошибке рендеринга.
Затем выполните обычные `install.py check` и `install.py install` по README.
Если проверка конфигурации не прошла, установку не запускайте; исправьте значения
или установите `enabled: false` и повторите `check`.

После установки проверьте актуальные применённые policies и повторите прикладную
проверку из README: `ready` и запрос через Uter в LiteLLM. Вместе с администратором
проверьте доступ к DNS по UDP и TCP, внутренние соединения и отказ к другим
реально слушающим адресатам/портам. Ошибка DNS или отказ неподнятого сервера сами
по себе не доказывают действие блокировки. Тестируйте с фактическим CNI и сетевыми
политиками корпоративного кластера.

## Снятие профиля и обновления

До первой установки для отключения замените `enabled: true` на `enabled: false`
в `<home>/values.yaml` и снова выполните `install.py check`.

Для уже установленного Helm release отключение — изменение сетевой защиты.
В отдельном согласованном окне укажите точный Kubernetes context и имя установки
(`NAME`, одновременно имя namespace), а также путь `CHART` к проверенному chart
**текущей установленной версии**. До принятия установки в управление это
`<home>/charts/uter`; после принятия — chart текущего подписанного выпуска в
`<home>/releases/<текущая-версия>/charts/uter`. Не подставляйте chart другой
версии и не продолжайте при незавершённом обновлении или восстановлении.

```bash
CONTEXT='укажите-context'
NAME='укажите-имя-установки'
CHART='/укажите/путь/к/проверенному/charts/uter'
helm --kube-context "$CONTEXT" upgrade "$NAME" "$CHART" \
  --namespace "$NAME" --reuse-values \
  --set networkPolicy.egress.enabled=false --wait --timeout 5m
```

Убедитесь, что
применены именно три ingress-политики без трёх egress-политик, и проверьте
работоспособность. Сохраните `enabled: false` также в файле конфигурации,
который будет использоваться при дальнейшем обновлении. Для новой установки это
`<home>/values.yaml`; после принятия управления обновлениями —
`<home>/runtime/values.yaml`. Не изменяйте chart внутри подписанного комплекта.
При неуспешном Helm upgrade и наличии предыдущей успешной ревизии сетевой
администратор может вернуть её через `helm rollback`; убедитесь, что сохранённый
файл values соответствует фактически применённой ревизии. Для самой первой
неуспешной установки предыдущей ревизии может не быть; не удаляйте namespace или
данные автоматически, действуйте по процедуре восстановления установки.

При принятии установки в управление текущий код копирует `<home>/values.yaml` в
`<home>/runtime/values.yaml`. Управляемое обновление читает второй файл и
добавляет значения образов нового подписанного выпуска отдельным файлом; при
восстановлении используется сохранённый `runtime/values.yaml`. Это поведение
подтверждено чтением кода, но сохранение этого нового egress-профиля при реальном
обновлении и восстановлении ещё требует отдельной проверки. После смены версии,
CNI, DNS, сети или адреса LiteLLM повторно проверяйте фактическое применение и
соединения. Ручное включение в уже работающей установке этой инструкцией не
автоматизировано: сначала проверьте процедуру на отдельной установке.

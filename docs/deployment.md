# Установка и обновление окружения

## Граница первого профиля

Linux amd64, Python 3.12 для контроллера, Docker Compose >=2.30 либо Helm 3.17.3
и Kubernetes >=1.27. Поддержка конкретной версии Kubernetes требует теста в контуре.
Один экземпляр каждого сервиса; при обновлении возможен простой. Доступ снаружи —
через TLS reverse proxy/Ingress окружения. В Compose порт Guardrail привязан к localhost;
в Helm только ClusterIP. Не открывайте Agent и Redis наружу.
NetworkPolicy ограничивает ingress при наличии поддерживающего CNI. Egress,
внутрикластерный TLS и внешние CA настраиваются инфраструктурой окружения.

## Постоянный каталог

```
/srv/uter/
  runtime/
    site.json
    guardrail.env
    agent.env
    redis.conf
    redis-password
    audit-hmac-key
    policies/runtime.toml
    profiles/model_profiles.toml
    models/
    acceptance.py
    values.yaml                 # для Helm вместо Compose env-файлов
  releases/                     # проверенные неизменяемые комплекты
  state.json                    # current / previous / pending
```

Скопируйте примеры в `runtime/` один раз и заполните. Контроллер их не переписывает.
`site.json` определяет backend, постоянное имя установки и namespace. Не меняйте их
между обновлениями: иначе получите другую установку и другие тома. Имя не должно
совпадать с существующим стендом разработчика.

Пароли для ADMIN/USER/SERVICE в guardrail задаются bcrypt-хешами; агенту нужен
соответствующий SERVICE plaintext password. Shared secret в обоих сервисах совпадает.
В raw env_file не заключайте значения в кавычки: кавычки станут частью значения.
Redis password в `redis.conf` и `redis-password` должен совпадать.
Файлы секретов: владельцы/права должны разрешать чтение только администратору
и нужному UID контейнера. Не печатайте развёрнутый `compose config` с реальными env.
Секреты приложения доступны администратору Docker/Kubernetes — это не защита от root.

Политики, профили и модели выдаются как отдельно согласованные runtime-ресурсы.
Не копируйте весь каталог разработки. Пути моделей в политике должны указывать
на `/app/models/...`; toxicity-модель должна быть предзагружена в runtime image.
Изменение моделей/политик тестируется отдельно, контроллер их не заменяет автоматически.
Для RAG настройте реальные интеграции: продукт содержит встроенные демонстрационные
registry, поэтому готовность HTTP сама по себе не подтверждает реальные данные.

## Первая установка Compose

Инструкция предназначена для отдельного сервера после выпуска настоящего
комплекта. Не выполнять её в каталоге или под именем работающего стенда разработки.
Tooling должен включать `examples/`, `requirements.txt` и `uterctl.py`; bundle и
runtime-ресурсы поставляются отдельно. Нынешний bundle builder не включает examples.

От имени оператора с правами подготовки `/srv/uter`, из каталога tooling:

```bash
umask 077
mkdir -p /srv/uter/runtime/{policies,profiles,models}
cp -n examples/site.json /srv/uter/runtime/site.json
cp -n examples/guardrail.env.example /srv/uter/runtime/guardrail.env
cp -n examples/agent.env.example /srv/uter/runtime/agent.env
cp -n examples/redis.conf.example /srv/uter/runtime/redis.conf
```

Заполнить до `check`:

| Файл | Что подготовить |
|---|---|
| `site.json` | Уникальное постоянное name, backend=compose, smoke_command с рабочим интерпретатором и acceptance.py |
| `guardrail.env` | JWT_SECRET, bcrypt-хеши трёх паролей, общий секрет Agent, реальные URL/model/key LLM и ingress secret |
| `agent.env` | Тот же общий секрет и plaintext пароль SERVICE, соответствующий SERVICE_PASSWORD_HASH |
| `redis.conf`, `redis-password` | Один и тот же случайный пароль; в redis-password только значение |
| `audit-hmac-key` | Отдельный случайный ключ; сохранить для проверки существующей цепочки при обновлении |
| `policies/runtime.toml` | Согласованная политика из runtime-артефактов |
| `profiles/model_profiles.toml` | Согласованные профили моделей |
| `models/` | Согласованные локальные модели при необходимости; каталог обязателен даже пустой |
| `acceptance.py` | Проверки оператора с ненулевым exit code при ошибке; готового универсального файла в examples нет |

Секреты создавать криптографическим генератором, отдельно друг от друга, не использовать
пароли из CI. Bcrypt-хеш строится из того пароля, которым будет выполняться вход;
не вставлять plaintext вместо хеша. Не использовать `source guardrail.env`: это raw
Compose env, символы `$` в bcrypt должны оставаться буквальными.

После `umask 077` назначить минимальные права чтения нужным пользователям контейнера:
Guardrail/Agent UID 10001, Redis UID 999 (GID 1000). Redis password читают и Redis,
и Guardrail; аудитный ключ — Guardrail. Для совместного доступа применить ACL или
согласованную схему групп. Политики, профили и модели должны читаться UID 10001.
Не делать весь runtime доступным всем. Env-файлы читает оператор Compose; файлы,
смонтированные через secrets/volumes, должны читаться соответствующим UID внутри.

Если образы в private registry, оператор предварительно выполняет `docker login`
с ограниченным read-only credential. Затем выполнить команды verify/check/apply
из README. Они используют digest из подписанного bundle, а не тег latest.
Первый запуск должен завершиться успешным acceptance; один ответ `/ready` недостаточен.

## Helm

Установите `"backend": "helm"` в site.json,
задайте постоянные name/namespace. Создайте namespace и ресурсы из `examples/values.yaml`
до запуска apply; modelsClaim должен быть Bound, а выбранный StorageClass — рабочим:

- `guardrailSecret`: env-ключи из guardrail.env плюс `AUDIT_LOG_HMAC_KEY`.
- `agentSecret`: env-ключи из agent.env.
- `redisSecret`: ключ `password`.
- `policyConfigMap`: ключ `runtime.toml`.
- `profileConfigMap`: ключ `model_profiles.toml`.
- `modelsClaim`: подготовленный PVC с моделями.

Скопируйте `examples/values.yaml` в `runtime/values.yaml`, заполните endpoint LLM.
Для private registry добавьте `imagePullSecrets`. Выдайте оператору необходимые RBAC.
Контроллер не читает Secret из кластера; существование и содержимое проверяются при
установке/acceptance. Кастомные Env не должны дублировать фиксированные служебные ключи.
PVC аудита и Redis помечены keep; uninstall не является удалением данных.

## Проверка и применение

Установите контроллер и зависимости из доверенного релиза tooling. Публичный Ed25519
ключ издателя получите независимо от скачанного комплекта. `verify` проверяет именно
этот ключ. Доверие ключу не устанавливается автоматически.

Для установки, принятой из `install.py` под управление `uterctl`, перед обновлением
обязательны `--backup-dir` (новый каталог вне установки) и `--backup-key` (отдельный
ключ шифрования). Контроллер останавливает пишущие компоненты, создаёт и проверяет
зашифрованную копию runtime, Redis и аудита, затем запускает обновление. Приёмка
установки требует подписанного комплекта текущей версии и доверенного ключа издателя.
Подписанных пользовательских комплектов пока нет; тестовые ключи CI не подходят.

Для более ранних установок, созданных непосредственно через `uterctl` и не принятых
из `install.py`, существует прежний режим подтверждения оператора receipt:

```json
{"version":"1.0.0","backup_id":"storage-snapshot-2026-10-22-001"}
```

Для этого режима receipt не является проверкой копии: оператор сам отвечает за
согласованные снимки и проверку восстановления. Внешние системы и модели требуют
своих процедур. Миграции данных контроллер не запускает.

`acceptance.py` — тест окружения с ненулевым exit code на ошибке. Обязательные сценарии:
авторизация, обычный запрос, блокировка опасного запроса, сохранение аудита и реальные
источники RAG (если используются). Его путь/аргументы находятся в `smoke_command`.
Это доверенная команда окружения, выполняемая на машине оператора без shell.

## Сбой и откат

`pending` означает, что часть сервисов уже могла измениться. Сначала изучите состояние.
Для установки, принятой из `install.py`, `resume` требует ту же версию и проверенную
копию, созданную перед прерванным обновлением. Автоматический `rollback` при `pending`
намеренно заблокирован: сначала нужно проверить и восстановить данные. Полное
автоматическое восстановление рабочих компонентов пока не реализовано; экспорт копии
через `scripts/restore_backup.py` не меняет рабочие данные. Для старого режима с receipt
контроллер может переключить версии, но не восстанавливает данные. Смена data_epoch
запрещена до отдельной процедуры миграции.

Для проверки содержимого можно экспортировать копию в новый защищённый каталог и
распаковать архивы в отдельные подкаталоги:

```bash
python3 scripts/restore_backup.py --backup /path/to/backup \
  --backup-key /path/to/backup.key --output /private/new-recovery-directory --stage
```

Родитель выходного каталога должен существовать; сам каталог не должен существовать.
Он содержит расшифрованные секреты, настройки и данные: ограничьте к нему доступ и
удалите после проверки. `--stage` не запускает сервисы и не восстанавливает Redis,
PVC или volumes. При ошибке маркер `INCOMPLETE` указывает на незавершённую подготовку.

Дополнительная предварительная проверка для доступного исходного каталога установки:

```bash
python3 scripts/recovery_preflight.py --home /path/to/installation \
  --backup /path/to/backup --backup-key /path/to/backup.key \
  --publisher-key /path/to/trusted-publisher.pem --output /private/new-preflight-directory
```

Она проверяет подлинность копии и её привязку к указанной установке, подпись
сохранённого комплекта и состав ресурсов Kubernetes, затем готовит приватный каталог
с данными. Команда не изменяет сервисы, volumes или PVC и не выполняет переключение.
Ей нужен существующий исходный каталог установки; восстановление при его полной потере
ещё не реализовано. Выходной каталог содержит расшифрованные секреты и данные.

При сбое самой первой установки предыдущего комплекта нет: используется `resume`.
После аварийного завершения процесса может остаться operation.lock. Удалять его можно
только убедившись, что другой uterctl не работает. Не удаляйте state.json ради обхода проверок.

## Закрытый контур

Перенесите проверенный комплект, образы и модели разрешённым каналом. Образы импортируйте
во внутренний registry с сохранением manifest digest или заранее загрузите на нужные
узлы. Если меняется адрес registry, сопровождающий должен выпустить и подписать соответствующий
manifest. Не редактируйте подписанные файлы. Для Compose `--offline` запрещает pull;
нужные digest references должны уже разрешаться локально (проверить до окна обновления).
Для Kubernetes заранее обеспечьте доступ к внутреннему registry или кеши всех узлов;
флаг offline не управляет сетевой политикой kubelet. HF offline включён только у Guardrail;
модели внешних систем и embeddings надо подготовить отдельно.

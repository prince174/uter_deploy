# Граница экспериментального обслуживания Kubernetes

Этот документ описывает требования к будущему безопасному обновлению, а не
готовую инструкцию. Пользовательское обновление через `uterctl`, создание backup
и миграция на основании этих экспериментальных функций не разрешены.

## Что уже фиксируется

Подготовка может записать под защищённой блокировкой неизменяемую HMAC-запись
с привязкой к журналу операции, подписанному manifest и проверенным UID Pod,
Deployment, Secret, ID контейнеров и хешам спецификаций Agent и Guardrail.
Она не подтверждает наличие сетевой изоляции. Следующее чтение заново проверяет
эти идентификаторы и подпись журнала. Изменение, перезапуск, отсутствие Pod,
недоступный API или повреждённая запись блокируют продолжение. Readiness после
начала drain может стать false, но сама по себе не является подтверждением
завершения запросов. До первого запроса требуется готовность обеих служб.
Для Secret также фиксируется `resourceVersion`: изменение объекта с прежним
UID будет обнаружено, но значение ключа в журнал не записывается.

Путь к coordinator и запись отдельных intent и receipt подготовлены, но
текущий gate безусловно блокирует вызов maintenance. Ни один параметр оператора
не может включить его. Таким образом, проверенный inventory сам по себе не
разрешает ни POST, ни резервное копирование, ни обновление.

## Доказательства до открытия gate

* **Управление источниками и перезапуском.** Должен быть зафиксирован внешний
  доверенный профиль кластера и политика admission/RBAC, запрещающая менять
  Pod, Deployment, Secret, масштабирование, ephemeral containers и процессы
  помимо контролируемых переходов. На всём интервале должны проверяться имена,
  UID и идентичность контейнеров и процессов. Отсутствие liveness probe не
  предотвращает аварийный перезапуск kubelet. Наблюдаемое Kubernetes API
  состояние может отставать от фактического процесса, поэтому одной периодической
  проверки `restartCount` недостаточно для атомарного доказательства.
* **Ingress.** Нужна независимо проверяемая и удерживаемая блокировка новых
  запросов ко всем экземплярам, включая прямые обходные пути, а также проверка
  уже установленных соединений. Проверка лишь через Service или один тестовый
  Pod не доказывает отсутствие остальных путей. NetworkPolicy аддитивны, их
  исполнение зависит от CNI; настройка политики сама по себе не доказывает
  прекращение ранее установленных соединений.
* **Доступ к Redis.** Нужен подтверждаемый и удерживаемый контроль всех
  возможных писателей и действующих сессий, включая прямые обращения, доступ
  из других namespace, host-network, порты API и привилегированные пути. Для
  узкого профиля необходимы независимо утверждённые Redis ACL, учёт и проверка
  активных соединений, обеспеченное прекращение недопустимых соединений и
  проверенная политика сети в дополнение к доверенным node/control-plane
  администраторам. Ротация секрета или добавление NetworkPolicy без проверки
  существующих сессий не является достаточным доказательством.
  В отдельном эксперименте исследуется профиль с заранее созданным admin ACL
  и пользовательским `default`: запрет новой аутентификации default,
  `CLIENT KILL USER default` и проверка оставшихся соединений. По
  [документации Redis](https://redis.io/docs/latest/commands/acl-setuser/),
  отключение пользователя не закрывает уже аутентифицированные подключения.
  Эксперимент не подключён к установке и не даёт права создавать backup.
  Текущая конфигурация Redis использует `requirepass`, без отдельного admin;
  пользователь default имеет административные права, поэтому эксперимент
  отклоняет его до какой-либо мутации. Синтетический тест предварительно
  ограничивает default до PING/GET/SET; это не проверенный список для Uter.
  До внедрения такого профиля необходимо доказать сохранение и восстановление
  ACL после сбоя и перезапуска и защиту admin-ключа.

  Для проверки возможного ACL требуется больше команд, чем в синтетическом
  эксперименте: в изученном Guardrail (`500ff6c`) rate limiter использует `EVAL` и Lua
  `INCR`/`TTL`/`EXPIRE`, approvals — `SET` и Lua `GET`/`DEL`, история —
  `LPUSH`/`LTRIM`/`LRANGE`/`EXPIRE`/`DEL` и транзакционный pipeline, правила —
  операции над множествами и хешами Redis. Для Redis-клиента также необходимо учесть команды
  протокола подключения и управления транзакцией. Этот список получен из
  статического чтения и не считается полным ACL: нужны динамические сценарии
  startup/readiness, отказов, истории, approvals, rules, rate limiter, фоновых
  задач и поведения используемой версии Redis-клиента. Разрешение `EVAL` не
  заменяет проверку прав на вызываемые из Lua команды и ключи.

  [Одноразовый CI 41136980007](https://github.com/prince174/uter_deploy/actions/runs/41136980007)
  прошёл на защищённых образах с отдельным тестовым admin и ограниченным ACL
  default. Проверены запуск/readiness, тестовые запросы, rate limiter и Lua,
  история с pipeline, изменение правил, выдача и однократное использование
  approval, отказ обычному пользователю в административной команде и повторный
  основной acceptance после перезапуска. Это не полный перечень путей Uter,
  не проверка сбоя ACL/Redis и не разрешение использовать профиль в production.
* **Квитанции и состояние данных.** После исключения гонок координатор обязан
  получить и сохранить receipt от каждого Agent, затем от каждого Guardrail,
  сверить boot ID и убедиться, что все они относятся к прежним процессам. До
  снимка необходимо подтвердить закрытие Redis-клиентов, полную целостность
  аудита и согласованность данных, а после восстановления — проверку данных и
  здоровья до повторного допуска писателей.

## Отказы и восстановление

Неизвестный результат POST нельзя повторять автоматически: операция остаётся
заблокированной до проверки состояния и подходящего пути восстановления. Потеря
процесса, смена UID, повреждение evidence, истечение доступа к API, конфликт
управляющих контроллеров, тайм-аут, невозможность подтвердить исключение
писателей или неуспешная проверка Redis/аудита должны запрещать backup и update.
Сценарии восстановления из каждой точки сбоя необходимо проверить в отдельном
одноразовом кластере на реальных образах; такие проверки пока не завершены.

Неоднозначные владельцы старой истории остаются отдельным блокирующим условием.
Для их безопасного сопоставления нужен достоверный источник; наличие
квитанций обслуживания не подтверждает корректность миграции.

## Возможное расширение контракта Uter

Существующее подтверждение привязано к одному `boot_id`: после перезапуска
процесс начинает работу заново. Для автоматического восстановления без окна
записи можно отдельно реализовать в Uter устойчивый режим обслуживания с
монотонным идентификатором операции и состоянием во внешнем надёжном хранилище.
Каждый новый процесс обязан проверить это состояние **до** приёма запросов и
любого открытия Redis для записи и, пока операция активна или проверка не
удалась, оставаться закрытым. Снять режим можно только отдельным проверяемым
переходом для той же операции и после успешного восстановления. Требуются
тесты атомарности при падении, параллельном запуске нескольких реплик,
потере хранилища и попытке использовать устаревший идентификатор.

Такое расширение не является заменой внешнему контролю Redis: другие
авторизованные писатели и привилегированные операторы всё равно могут обходить
Uter. Текущий протокол такого устойчивого режима не предоставляет; здесь он
не реализован и не используется как доказательство.

## Проверка в одноразовом kind

[Запуск CI 41136172035](https://github.com/prince174/uter_deploy/actions/runs/41136172035)
на коммите `355cbce` завершился успешно. В отдельном kind были запущены
защищённые образы Agent и Guardrail и зафиксированы UID Pod и контейнеров.
Тест создал на этом же runner временную подпись, доверенный ключ, kubeconfig,
HMAC-профиль schema 2 и фиктивное состояние принятой установки. Из подписанной
копии executor командой `python -I` был вызван `maintenance-check-kubernetes`.
Он вернул сведения о двух Pod и явно указал, что endpoint приложения, сетевые
ограждения и возможность обновления не подтверждены.

Отдельный тест с заменой проверки подписи на fixture затем получил квитанции
Agent и Guardrail, обнаружил изменение Secret по resourceVersion и отверг
inventory после удаления Pod. Это проверяет только перечисленные сценарии в
тестовом кластере. Источники доверия сгенерированы самим runner; независимая
проверка профиля реальной организации, непрерывная изоляция Redis, резервное
копирование, миграция и восстановление не проверялись.

[Следующий запуск CI 41143575690](https://github.com/prince174/uter_deploy/actions/runs/41143575690)
проверил read-only transport к настоящему Redis Pod через подписанный
тестовый executor, pinned `kubectl`, `nc` и ограниченный RESP2. Тестовая
admin-аутентификация передавалась в stdin; неверный `run_id` и старая запись
плана после реальной замены Pod приводили к отказу. Это только проверка
выбранных команд и двух снимков идентичности при доверенном Redis и управляющей
плоскости. Подписи, профиль и admin были тестовыми; HMAC ACL intents, защита
от внешних писателей, непрерывная неизменность Pod, backup, обновление и
восстановление в этом запуске не подтверждались. Transport остаётся отдельным
экспериментом и не подключён к пользовательскому обновлению.

## Потеря управляющего Redis-соединения

При падении executor ранее записанный Redis `CLIENT ID` нельзя использовать
для нового соединения: новое подключение получает новый идентификатор. Поэтому
простое подключение заново не является восстановлением и не позволяет повторять
неопределённые команды. Исследуемый read-only transport проверяет новый ID и
`run_id` только в течение одной живой сессии, а также UID и идентификатор
контейнера Redis по плану; он не приравнивает её к старой и не открывает gate.

Для будущего безопасного перехода нужно отдельное подписанное намерение,
привязанное к operation journal, старому ID, `run_id`, Pod и авторизованному
executor. Оно должно запрещать повтор ACL-операций и предусматривать проверку
отсутствия прежнего и посторонних admin-соединений, регистрацию нового ID и
устойчивую запись результата до дальнейших действий. Изменение процесса Redis,
UID Pod, ACL, прав доступа или неизвестный исход должны сохранять блокировку.
Нужны независимый контроль прав и внешних писателей, а также испытания потери
процесса до/после каждой записи и каждого ответа. Такой переход пока не
реализован; автоматическое восстановление по нему недоступно.

## Подготовка будущего сохранения maintenance Secret

В коде резервного копирования и восстановления предусмотрена проверка для
будущей установки с явным `maintenance_enabled: true`. Она требует объявление
протокола в проверенном подписанном manifest, отдельный закрытый локальный файл
ключа и одноимённый Kubernetes Secret, содержащий тот же ключ. Secret будет включаться
в зашифрованный резервный набор; подготовлен код переназначения его имени при
восстановлении в новый namespace. Отсутствие файла, Secret, необходимого
объявления или совпадения ключей приводит к отказу. Без этого маркера действует
прежний режим.

Это подготовительный код: установщик пока не включает этот режим, а поддержка
Secret сама по себе не доказывает безопасность резервного копирования,
обновления и восстановления работающего сервиса. Kubernetes RBAC и шифрование
Secret в хранилище кластера настраиваются администратором кластера; локальная
постановочная директория восстановления также содержит конфиденциальные данные.
Восстановление opt-in установки пока явно запрещено: для него необходимы
подписанный Helm profile и проверка фактического подключения секрета к обоим сервисам.

### Подготовительный Helm profile

Chart содержит выключенный по умолчанию профиль `maintenanceEnabled`. При
включении он предполагает отдельный Secret `<release>-maintenance` с ключом
`key`, монтирует его только для Agent и Guardrail в режиме чтения с правами
0440 и задаёт `WEB_CONCURRENCY=1`. Явные значения maintenance-переменных в
пользовательских `agentEnv` и `guardrailEnv` запрещены; это касается и ручных
старых конфигураций, если в них ранее добавлялись такие переменные.

Экспериментальная проверка сверяет подпись и точные хеши всего chart с
зафиксированным проверенным вариантом, digest образов (в том числе при замене
адреса registry), значения Secret и отсутствие повторного использования ключа
в переданных снимках служебных Secret. Это проверка снимка, а не живого Pod:
она не доказывает, что Helm впоследствии применит именно проверенные файлы,
что Secret смонтирован или что реально работает один процесс. Для любого
изменения chart потребуется обновить привязку и повторить проверки. Прямой
ручной запуск Helm сам по себе не проверяет подписанную capability.

Установщик не включает этот профиль. Обновление и восстановление opt-in
установки остаются заблокированными до проверки применённой конфигурации,
процессов, изоляции Redis и безопасного восстановления.

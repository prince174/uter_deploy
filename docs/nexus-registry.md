# Загрузка образов через корпоративный Nexus

Этот документ описывает подготовку Docker-репозитория Nexus для установки Uter.
Nexus предоставляет образы, но не заменяет проверку подписанного выпуска,
доверия к издателю и совместимости версии. Поддержка выбора других путей
образов разрабатывается в текущем дереве `uter_deploy`. Опубликованный мастер
`deploy-2026.10.29-signed-4` / `0.1.6` этих параметров не содержит. Новый мастер
работает с проверенным подписанным комплектом, не переписывая его; сведения о
работе исходного выпущенного мастера от этого не меняются. Не изменяйте
подписанные файлы выпуска вручную.

**Граница функций:** для установки с заменёнными путями штатные принятие под
управление, обновление, резервное копирование и восстановление опубликованной
версии `0.1.6` пока не поддержаны. Принятие такой установки под управление
отказывает. Старые опубликованные контроллеры не знают о выборе других путей,
и восстановление может обратиться к GHCR; не запускайте старые команды
обновления и восстановления для такой установки. Запрет обеспечивается не
всеми ранее выпущенными контроллерами. Не используйте такую установку там, где
уже нужны перечисленные операции, до их реализации и проверки для вашей среды.

## 1. Подготовить Nexus

Администратор Nexus должен предоставить Docker Registry API endpoint, доступный
для соответствующего Docker daemon или каждого узла Kubernetes, и подготовить
три репозитория образов Uter: Guardrail, Agent и Redis. Это может быть Docker
proxy/group с доступом к GHCR либо hosted-репозиторий, в который образы заранее
скопированы по принятому в организации процессу. Для изолированной сети
проверьте, что нужные версии и все их слои уже доступны внутри организации.

Для каждого сервиса необходимо знать полный путь к образу **без тега и без
`@sha256`**. Администратор может использовать разные пути для разных сервисов;
один репозиторий для нескольких образов тоже допустим, поскольку исходные digest
различают манифесты. Первая часть пути должна явно определять registry для
Docker: содержать точку в имени хоста, порт либо быть `localhost`. Например,
`nexus:5000/team/image` допустим, а `nexus/team/image` не подходит.
Примеры формата ниже иллюстративны; адреса и имена необходимо заменить на
реальные, выданные администратором:

| Способ маршрутизации Nexus | Пример пути к одному образу |
|---|---|
| Отдельный HTTPS port connector | `nexus.example.internal:18443/prince174/uter-guardrail` |
| Поддомен или reverse proxy | `docker.example.internal/prince174/uter-guardrail` |
| Включённый path-based routing | `nexus.example.internal/docker-proxy/prince174/uter-guardrail` |

Не подставляйте автоматически адрес веб-интерфейса вида
`https://nexus.example.internal/repository/docker-proxy/`: Docker-клиентам нужен
правильно настроенный endpoint Registry API. Path-based routing и его доступность
зависят от версии и конфигурации Nexus; в примере для него не используется
`/repository/`. Разные режимы маршрутизации описаны в официальной
[документации Sonatype](https://help.sonatype.com/en/docker-registry.html).

## 2. Проверить содержимое и доверие

- Выпуск определяет неподменяемый SHA-256 digest каждого образа. Внутренние пути
  должны предоставлять **те же digest**; одинаковый тег или имя не доказывает,
  что манифест и содержимое совпадают. Копирование, которое пересоздаёт или
  преобразует манифест, может изменить digest: такой образ не подходит для
  установки по исходной подписи без отдельного доверенного процесса выпуска.
- Клиент, отправляющий запрос на скачивание, должен доверять сертификату Nexus.
  Для Compose это Docker daemon на сервере, а не только терминал пользователя;
  для Kubernetes — container runtime каждого потенциального узла. Настройка CA
  для LiteLLM внутри Guardrail не настраивает доверие к registry.
- Если Nexus требует авторизацию, подготовьте отдельную учётную запись с правом
  только на чтение нужных образов. Не помещайте пароль в командную строку, Git,
  чат или логи. Важно проверять доступ именно того daemon или kubelet, который
  будет скачивать образы, и учитывать срок действия учётных данных.
- Доступ к Nexus не обеспечивает доступ к подписанному выпуску, Git и
  Python-зависимостям. При закрытом интернете их также надо доставить и проверить
  по разрешённому процессу. LiteLLM остаётся отдельной сетевой зависимостью.

## 3. Доступ Compose и Kubernetes

Для Compose используйте доверенный Docker CLI и выделенную защищённую Docker
конфигурацию. Вход в Nexus выполняется для `hostname[:port]` без пути репозитория.
Например, для root-owned каталога `/secure/docker` выполните
`sudo docker --config /secure/docker login nexus.example.internal:18443`;
пароль вводится в интерактивном запросе. Каталог и созданный в нём `config.json`
должны быть доступны только оператору или root; конфигурация должна содержать
inline `auths`, без credential helpers. Перед установкой проверьте доверие CA и
возможность получения нужных digest с этой конфигурацией. Этот пример не меняет
общий Docker config пользователя. Подробности входа:
[Sonatype Docker Authentication](https://help.sonatype.com/en/docker-authentication.html).

Для Kubernetes узлам необходимы доступ к Nexus и доверие к его TLS-сертификату.
Для приватного endpoint нужен `imagePullSecret` с правом чтения и его применение
к Pod в правильном namespace. Наличие credential helper на рабочей станции не
означает, что kubelet может его выполнить. При использовании `--registry-config`
установщик принимает Docker `config.json` с inline `auths` и создаёт Secret;
защитите этот файл и сгенерированный `resources.yaml`, содержащий секреты.
Kubernetes Secret сам по себе не гарантирует шифрование данных на диске кластера.
Подробнее: [Pull an Image from a Private Registry](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/).

## 4. Передать пути установщику

В разрабатываемой версии мастера при интерактивной установке выберите вариант
корпоративного registry и укажите полные пути для **всех трёх** сервисов. Их
также можно передать параметрами команды:

```text
--image-guardrail-repository nexus.example.internal:18443/prince174/uter-guardrail
--image-agent-repository     nexus.example.internal:18443/prince174/uter-agent
--image-redis-repository     nexus.example.internal:18443/prince174/uter-redis
```

Используйте реальные пути Nexus; примеры не являются действующими адресами.
Путь задаётся без `https://`, тега и `@sha256`. Мастер проверяет оригинальный
подписанный комплект и входные данные, затем формирует отдельный временный список
образов с выбранными путями и **исходными подписанными digest**. Подписанный
manifest и архив выпуска не изменяются. Если digest недоступен по указанному
пути, установка не должна подменять его тегом или другим digest.

Для Compose передайте эти параметры команде `bootstrap_wizard.py install` с
`--backend compose`; для Kubernetes — той же команде с `--backend kubernetes`.
Базовые команды, новые каталоги и параметры LLM описаны в
[инструкции мастера](wizard.md). Используйте доверенный checkout, содержащий
эти изменения: скрипт, извлечённый из опубликованного тега `0.1.6`, параметры
путей не понимает. Для приватного Nexus на любой платформе дополнительно передайте
`--registry-config /secure/docker/config.json` с непустым набором inline `auths`
и допустимыми правами доступа. В `auths` разрешены только выбранные registry
hosts; можно указать непустое подмножество, остальные будут анонимными.
Мастер сам вход в registry не выполняет. Для Compose он
передаёт доверенную приватную конфигурацию процессу установки через
`DOCKER_CONFIG`; одного `docker --config ... login` без этого параметра мастера
недостаточно. Параметр передаётся после `sudo`, поэтому не зависит от сохранения
пользовательских переменных среды политикой `sudo`. Эта конфигурация используется
только при установке: для последующей загрузки или пересоздания контейнеров
оператор отдельно настраивает доверенный Docker login/config. Для Kubernetes
созданный Secret используется как `imagePullSecret`.

Если корпоративный registry не выбран и пути не заданы, остаются адреса из
подписанного выпуска. При выборе Nexus нужны все три пути; неполный набор не
принимается. Не включайте логин или пароль в путь репозитория. Переписывание
адреса не переносит образы в Nexus автоматически.

После установки проверьте скачивание всех трёх образов, готовность контейнеров
или Pod и авторизованный запрос через Uter к реальному LiteLLM/vLLM. Успешная
проверка с управляющего хоста не подтверждает доступ registry и CA на узлах.
Использование Nexus также не снимает ограничений обновления `0.1.6 → 0.1.7`.

Реальный Nexus и корпоративные сетевые политики должны быть отдельно проверены
в целевой среде; наличие этого руководства само по себе такую проверку не заменяет.

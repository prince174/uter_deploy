# Эксперимент: запрет новых Redis AUTH перед drain

Это экспериментальная библиотека и отдельный disposable CI. Она не подключена к
`uterctl` или установщику, не меняет текущую `requirepass` конфигурацию и не
разрешает backup, обновление или восстановление. Для неё подготовлен отдельный
подписываемый профиль `compose/redis-acl-maintenance.json`; он описывает
ограниченный набор команд **для выбранных CI сценариев**, а не полное покрытие
всех функций Uter. Профиль проверяется вместе с подписанной capability двух
сервисов; доверие к ключу издателя и исполнителю задаёт вызывающая сторона.

Схема опыта предполагает выключенный default user, отдельного ограниченного
writer `uter-writer` и отдельного администратора с другим паролем. До изменения
проверяются Redis run ID, постоянное admin-соединение, пользователи и их права,
репликация, модули, функции и AOF. Затем вызывающая сторона должна записать
durable intent, после чего `ACL SETUSER uter-writer off` запрещает новые AUTH.
Уже аутентифицированные соединения не закрываются и могут завершать работу.
После **отдельного подтверждения drain**, проверок и ещё одного intent выполняется
`CLIENT KILL USER uter-writer`, затем проверяется отсутствие writer-соединений.

Неизвестный исход любой стадии приводит к `uncertain`: объект запрещает повтор
и не делает автоматический rollback. Для предоставленных callbacks библиотека
проверяет только возвращаемое значение; настоящие непрерывный ingress fence,
идентичность процесса, authenticated receipts и их crash recovery необходимо
обеспечить снаружи. Сам callback не доказывает drain. На restart Redis
проверка другого `run_id` запрещает продолжение, но снимок не гарантирует
отсутствие записи до обнаружения рестарта. Сохранение ACL при crash и защита
файлов аудита отдельно не доказаны.

В synthetic CI запись журнала использует реальный HMAC, но lock, signing key и
drain намеренно фиктивные. Образ Redis не привязан digest к self-signed fixture
manifest: проверка подписи здесь демонстрирует только профиль, а identity guard
подменён. Проверяются работа ранее аутентифицированного
соединения после `off`, отказ нового AUTH, закрытие прежних клиентов после
фиктивного drain и отказ продолжения после рестарта Redis. Это не тест продукта
Uter и не гарантия корректности всех соединений в рабочей установке.

Вариант с постоянным ACL использует защищённую директорию, подключённую в
Redis read-only **как директория**. Сначала caller записывает intent, затем
создаётся OFF-файл на той же файловой системе, выполняются fsync файла,
атомарный rename и fsync каталога, проверяется содержимое и сохраняется receipt
с его версией. После этого допустим экспериментальный volatile `ACL SETUSER
off`. Файловый helper связывает writer/admin hashes с наблюдаемыми Redis ACL,
но сам не подтверждает Redis mount и не связывает callbacks с операцией: это
обязанность вызывающей стороны. `redis_acl_source_verified` остаётся `false`.

Ошибки и прерывание до подтверждения fsync оставляют неопределённое состояние:
без отдельного startup/recovery gate автоматически запускать Redis и writers
нельзя. CI с `SIGKILL` и последующим стартом Redis проверяет только конкретный
контейнер и файловую систему, а не выключение питания, сбой хоста, AOF,
восстановление клиентов или production fence. [Disposable CI](https://github.com/prince174/uter_deploy/actions/runs/41149212367)
подтвердил: после SIGKILL и повторного запуска конкретного Redis с read-only
ACL directory новый AUTH writer запрещён; в варианте с inline-конфигурацией
AUTH снова разрешён. Версия OFF-файла проверена до и после запуска, а старый
`run_id` не принят до intent/KILL. Это проверка синтетического сценария; Uter
и настоящие guard/drain в ней не участвовали.

В [отдельном disposable CI с образами Uter](https://github.com/prince174/uter_deploy/actions/runs/41152564050)
прошли два независимых сценария. Использовались образы из проверенного CI-снимка,
тестовый Redis с ACL и управляемый тестовый LLM. Доверие к снимку и фиктивному
подписанному профилю обеспечено настройкой CI; это не подписанный продуктовый
релиз и не проверка произвольной установленной версии.

* **Drain:** после прохождения acceptance тестовый LLM задерживает следующий
  POST; одновременно выполняется разрешённый `/chat`. До завершения запроса
  фиксируется ACL OFF: новое соединение writer не проходит AUTH, а прежнее
  остаётся работоспособным. После наблюдения `draining` с активным запросом
  тест отпускает LLM, проверяет ответ и receipts сначала Agent, затем Guardrail,
  и закрывает оставшиеся writer-соединения. Доказательство принадлежности
  задержанного POST конкретному запросу отдельно не установлено: сценарий
  полагается на отсутствие конкурирующих LLM-запросов в своей fixture.
* **Restart:** после тех же receipts отдельно перезапускается Guardrail. Отказ
  нового AUTH сопоставляется с IPv4 закреплённого контейнера в той же backend
  сети. Старый receipt после перезапуска запрещает KILL; уже открытый тестовый
  writer при этом остаётся доступен. Совпадение IP не защищает от подмены
  соседа в недоверенной сети.

В обоих сценариях профиль и lock фиктивные, контроль окружения принадлежит CI,
а отдельный synthetic writer демонстрирует состояние Redis. Даже успешный CI не
доказывает непрерывную изоляцию ingress и внешних Redis writers, полноценность
аудита и восстановления, корректность миграции истории или безопасность обновления.
Подключение к пользовательскому `uterctl` и разрешение update остаются закрыты.

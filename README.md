# Uter Deploy

Самостоятельное развёртывание Guardrail + Agent + Redis через Docker Compose или
Kubernetes/Helm. Для запуска нужны готовые образы, настройки и внешний LLM API.
Исходники сервиса и сборка на машине установки не требуются.

Если LiteLLM и vLLM уже работают в инфраструктуре, начните с
[подробной инструкции подключения и развёртывания](docs/corporate-litellm-deployment.md).
В ней описаны сетевые требования, входные данные, Compose, Kubernetes, проверки и
ограничения автоматизации. Инструкция использует выпуск
`deploy-2026.10.29-signed-4` / `0.1.6`. Перед установкой проверьте его подпись
и отпечаток издателя по независимому каналу. Ранее опубликован [кандидат signed-2](https://github.com/prince174/uter_deploy/releases/tag/deploy-2026.10.29-signed-2).

**Корпоративный Nexus:** [настройка адресов образов и доступа](docs/nexus-registry.md).
Мастер из текущего checkout позволяет установить подписанный комплект `0.1.6`
через выбранные репозитории Nexus, сохраняя его digest. Опубликованный мастер
`0.1.6` такой возможности не содержит; для установки с изменёнными путями
резервное копирование и обновление имеют существенные ограничения, описанные
в инструкции.

Для интерактивной установки используйте [мастер Uter](docs/wizard.md).
В текущем дереве новые обновления существующих установок через мастер,
`update_installation.py` и `uterctl apply` заблокированы: пока не подтверждены
безопасное завершение запросов и независимая изоляция всех писателей. Первичная
установка и предусмотренные команды восстановления ранее начатых операций
сохранены. Проверка плана не разрешает обновление.
Новые обычные и запланированные live backup работающей установки также
заблокированы до подтверждения тех же условий. Старые копии сохраняются;
достоверность их согласованности для работы под нагрузкой отдельно не доказана.
Первичная установка через legacy `uterctl apply` тоже отключена: он не резервирует
имя проекта или namespace и может затронуть уже существующий стенд. Для новой
установки используйте мастер или `install.py install`; их проверка занятости
имени является снимком и не защищает от одновременных действий доверенного
администратора или другого контроллера на том же Docker/кластере.

Уже опубликованные версии этих инструментов такого запрета не содержат;
запуск старого `uterctl` или старого мастера этим изменением не блокируется.
Исторические успешные CI-проверки ниже не доказывают безопасность обновления
нагруженной установки с внешними писателями. Проверки, запускающие ранее
опубликованные подписанные комплекты, проверяют их старый код и не подтверждают
новый запрет. Исторический workflow `real-llm-upgrade` отключён явной ошибкой
до загрузок и запуска сценария; аналогично отключён `scheduled-backup`.
Прежний legacy rollback с `pending` сохранён для совместимости, но его receipt
не подтверждает подлинность копии и сохранность данных: не считайте его
доказанно безопасным восстановлением.
Он подготавливает Python-окружение, спрашивает параметры и проверяет подписанный
комплект. Для Compose на Linux после независимой проверки отпечатка издателя
пример запуска из нового root-owned checkout:

```bash
sudo git clone --branch deploy-2026.10.29-signed-4 --single-branch \
  https://github.com/prince174/uter_deploy.git /srv/uter-deploy-tooling
cd /srv/uter-deploy-tooling
sudo python3 -I scripts/bootstrap_wizard.py
```

Выберите установку или обновление и следуйте подсказкам. Для Kubernetes выполните
аналогичные команды от пользователя с доступом к выбранному контексту; подробности,
безопасные пути, существующая установка и восстановление описаны в инструкции.
Git checkout, Python, источник зависимостей, Docker/Compose или kubectl/Helm и
каталоги `PATH` должны быть доверенными: bootstrap не удостоверяет собственный
код, системные исполняемые файлы или окружение.

## Тестовый снимок 0.1.7

Подписанный [снимок `0.1.7`](https://github.com/prince174/uter_deploy/releases/tag/deploy-2026.10.30-test-1)
**отозван**; подписанный архив удалён из публикации. Не используйте ранее скачанные
копии: старый контроллер может применить их без защитной проверки. Стабильным остаётся `0.1.6`:
в проверке обновления история, ранее записанная под пользовательскими alias, автоматически
не открылась. Тестовые записи физически сохранились, но без надёжного сопоставления
их нельзя безопасно отнести к конкретному пользователю.

Выбранная политика блокировки, создание копии и важное ограничение проверки внешних
писателей описаны в [барьере истории сессий](docs/session-identity-transition.md).
Подписанный [кандидат с барьером](https://github.com/prince174/uter_deploy/releases/tag/deploy-2026.10.30-gated-2)
проверен в [изолированном CI](https://github.com/prince174/uter_deploy/actions/runs/41024366249)
для Compose и Kubernetes, включая пробное восстановление копии. Он предназначен
только для испытаний: пока не подтверждён безопасный механизм изоляции внешних
писателей, переход с epoch 1 на epoch 2 блокируется даже при пустой базе.

В текущем репозитории добавлена [заглушка источника владельцев](docs/session-provenance-contract.md).
Она всегда отказывает и не является источником данных или миграцией; для рабочего
перехода нужны проверенный источник и безопасная изоляция записей Redis.
Ход разработки изоляции, лабораторные проверки и их ограничения описаны
в [документе по Redis](docs/redis-fence-development.md); механизм пока не
подтверждён и не включён в опубликованное рабочее обновление. В исходном дереве
есть экспериментальный same-epoch Compose путь, но его проверка остановилась
на неподтверждённом корректном завершении Guardrail. В текущем дереве начало
новых экспериментальных операций `fence-start-redis` и `apply --fenced-update`
заблокировано до подтверждения безопасного обслуживания и изоляции; восстановление
ранее начатых операций сохраняется. Это не готовая процедура обновления и не
разрешение на переход `0.1.6 → 0.1.7`.
Изменения ещё не включены в опубликованный кандидат. Особенности временных
файлов при резервном копировании старых комплектов описаны в
[инструкции восстановления](docs/managed-update-recovery.md).

гарантирует стабильность внешней инфраструктуры LLM. Прочитать безопасный код этапа
ошибки и найти дальнейшие шаги поможет [диагностика мастера](docs/wizard.md#диагностика-установки).

на Compose авторизованная проверка завершилась `CHAT_HTTP_504`. На момент сбоя
суммарный счётчик генерации vLLM составлял 1402 токена, выполнялся один запрос и
три ожидали в очереди. Это наблюдение за общими метриками, а не число токенов
одного запроса или доказанная причина сбоя.

Для управления длиной ответов в инструкции `signed-4` предусмотрен необязательный
`--llm-max-tokens` от 1 до 65536. Оставьте пустым, чтобы не задавать переменную;
при выборе учитывайте риск обрезанных ответов и то, что отдельные сценарии, включая
RAG, могут переопределять значение. Подбор и диагностика очереди описаны в
[руководстве мастера](docs/wizard.md#настроить-длину-ответа-llm).

## 1. Получить установочные файлы

На Linux amd64 установите Python 3.11+ (рекомендуется 3.12), поддержку создания
`venv` и `pip`, Git и curl. Например, в Ubuntu модуль `venv` может поставляться
отдельным пакетом для используемой версии Python. Для Compose нужны Docker и Compose >=2.30;
для Kubernetes — kubectl, kubeconfig и Helm 3.17.3. Узлы должны поддерживать linux/amd64,
создание PVC и исходящие соединения к registry и LLM.

Получите и **независимо сверьте** SHA-256 публичного ключа издателя:
`65be6fd9613fa7e879735fe5b453bfcb8c0e38911cd7429c9aac9c9afba676a2`.
Значение, полученное только из этого же репозитория, не подтверждает доверие к ключу.
Для первой проверки также нужны доверенные Git-репозиторий, Python и зависимости;
сами эти инструменты не могут удостоверить собственное происхождение.
Далее приведён ручной вариант. Для Compose, если команды запускаются через `sudo`,
сам checkout, `.venv`, проверенные файлы и их родительские каталоги должны быть
доверенными root и не доступны на запись посторонним; не запускайте от root код
или окружение, которые может подменить другой пользователь.

```bash
git clone https://github.com/prince174/uter_deploy.git
cd uter_deploy
git checkout deploy-2026.10.29-signed-4
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
mkdir -p incoming signed
curl -fL -o signed/publisher-public.pem \
  https://github.com/prince174/uter_deploy/releases/download/deploy-2026.10.29-signed-4/publisher-public.pem
curl -fL -o signed/signed-bundle.tar.gz \
  https://github.com/prince174/uter_deploy/releases/download/deploy-2026.10.29-signed-4/signed-bundle.tar.gz
echo '65be6fd9613fa7e879735fe5b453bfcb8c0e38911cd7429c9aac9c9afba676a2  signed/publisher-public.pem' | sha256sum -c -
.venv/bin/python scripts/extract_signed_bundle.py \
  --archive signed/signed-bundle.tar.gz --key signed/publisher-public.pem \
  --output signed/0.1.6
curl -fL -o incoming/installation-inputs.tar.gz \
  https://github.com/prince174/uter_deploy/releases/download/deploy-2026.10.29-signed-4/installation-inputs.tar.gz
curl -fL -o incoming/installation-inputs.tar.gz.sha256 \
  https://github.com/prince174/uter_deploy/releases/download/deploy-2026.10.29-signed-4/installation-inputs.tar.gz.sha256
.venv/bin/python signed/0.1.6/scripts/extract_release_inputs.py \
  incoming/installation-inputs.tar.gz incoming/installation-inputs.tar.gz.sha256 incoming/inputs \
  --bundle signed/0.1.6 --key signed/publisher-public.pem
```

Команда проверяет подпись комплекта и подписанный SHA-256 архива **до** его
распаковки. Установочные данные содержат `images.json`, `policy.toml`,
`model_profiles.toml` и метаданные публикации. Установщик и шаблоны ниже берутся
из проверенного комплекта. В подписанном манифесте выпуска `0.1.6` указаны
`data_epoch = 1` и переход только с `0.1.5`; переходы с остальных управляемых
версий не заявлены.
Кандидаты `signed-2`, `signed-3` и `signed-4` используют версию `0.1.6`: переход
между ними не заявлен; не используйте этот сценарий для `0.1.6 → 0.1.6`.
В проверенных `0.1.5` и `signed-2` образы продукта одинаковы, поэтому такой
переход не проверяет миграцию между разными сборками. Сверьте подпись и декларацию совместимости в
опубликованном комплекте до обновления.

Из доверенного checkout с `scripts/fetch_release.py` выпуск можно также получить одной командой:

```bash
.venv/bin/python scripts/fetch_release.py --release deploy-2026.10.29-signed-4 \
  --version 0.1.6 --fingerprint "$UTER_PUBLISHER_SHA256" --output ./verified-release
```

Переменная `UTER_PUBLISHER_SHA256` должна содержать отпечаток, полученный и
сверенный по независимому доверенному каналу. Каталог назначения должен быть новым.
В Linux его родитель должен принадлежать оператору и быть защищён от записи других
пользователей; проверяются и родительские каталоги. В Windows оператор отдельно
проверяет ACL родительского каталога: команда не умеет подтверждать его приватность.
Результат содержит `bundle/`, `inputs/` и `downloads/publisher-public.pem`;
для команд установки укажите эти пути вместо `signed/0.1.6` и `incoming/inputs`.
Команда принимает выпуски с подписанным хешем входного архива и не заменяет доверие
к самой копии tooling, Python и зависимостям. В ранее выпущенном `0.1.4` её нет.

## 2A. Установить через Compose

Используйте отдельный сервер и новое имя проекта. Ориентир по ресурсам: 4 логических
CPU, лимиты контейнеров суммарно 5 GiB RAM плюс запас ОС. В CI проверен малый профиль
с `--guardrail-cpus 2`; это не оценка производительности под нагрузкой.
Поддерживается локальный Docker context `default` с Unix socket; удалённый daemon
для установки с bind-mount не поддерживается.

Для публичных образов вход в GHCR и токен не требуются.

```bash
sudo .venv/bin/python signed/0.1.6/scripts/install.py prepare \
  --home /srv/uter-instance --backend compose --name uter-instance \
  --inputs "$PWD/incoming/inputs"
sudo .venv/bin/python signed/0.1.6/scripts/install.py check --home /srv/uter-instance
sudo .venv/bin/python signed/0.1.6/scripts/install.py install --home /srv/uter-instance
curl --fail http://127.0.0.1:18000/ready
```

Мастер спросит URL OpenAI-совместимого LLM, имя модели и скрыто API-ключ.
Пример base URL: `https://llm.example/v1`. Путь `/chat/completions` добавляется сервисом.
Для существующего LiteLLM укажите его адрес, а в качестве модели — разрешённый
alias LiteLLM, маршрутизированный на vLLM. Адрес должен быть доступен и доверен по TLS
именно из контейнера или Pod Uter. Для полного набора корпоративных доверенных CA
добавьте `prepare --llm-ca-bundle PATH`; это заменяет стандартный набор доверия
процесса Guardrail. mTLS, сеть и прокси установщик не настраивает.
Если ключ не нужен, оставьте его пустым. HTTP разрешается только явным
`--allow-http-llm` для доверенной внутренней сети.

`prepare` генерирует пароли и конфигурацию, ничего не запускает. `check` проверяет
рендеринг без обращения к daemon/LLM. `install` скачивает образы, выставляет права,
запускает сервисы и ждёт готовности до 300 секунд. Порт по умолчанию — 18000, изменить
можно через `prepare --port 18001`. Он привязан к `127.0.0.1`; для внешнего доступа
нужен TLS reverse proxy. Agent и Redis наружу не публикуются.

## 2B. Установить в Kubernetes

Нужен **новый namespace**, равный `--name`. `--context` обязателен; текущий context
в kubeconfig установщик не меняет. Нужны права создавать namespace, Secret, ConfigMap,
PVC, Deployment, Service и NetworkPolicy. Ingress и TLS настраиваются отдельно.

Публичные образы не требуют файла доступа к registry:

```bash
.venv/bin/python signed/0.1.6/scripts/install.py prepare \
  --home "$HOME/uter-k8s" --backend kubernetes --name uter-instance \
  --context MY_CONTEXT --inputs "$PWD/incoming/inputs"
.venv/bin/python signed/0.1.6/scripts/install.py check --home "$HOME/uter-k8s"
.venv/bin/python signed/0.1.6/scripts/install.py install --home "$HOME/uter-k8s"
kubectl --context MY_CONTEXT -n uter-instance get pods,pvc
kubectl --context MY_CONTEXT -n uter-instance port-forward svc/uter-instance-guardrail 18000:8000
# В другом терминале:
curl --fail http://127.0.0.1:18000/ready
```

При отсутствии default StorageClass добавьте `prepare --storage-class YOUR_CLASS`.
Создаются PVC Redis 2 GiB и аудита 10 GiB, Secret и ConfigMap.
Проверенные образы содержат toxicity-модель; отдельный models PVC не нужен.
Для дополнительных моделей — [расширенные настройки](docs/deployment.md).

Если используется отдельный приватный registry, `--registry-config` принимает файл
с inline `auths`; credential helpers внутри Kubernetes не запускаются.
Для внешнего Ingress используется namespace `ingress-nginx`; если он другой,
измените `ingressNamespace` в сгенерированном `values.yaml` **до** install.

## 3. Проверить работу с реальным LLM

Пароли учётных записей `admin`, `user`, `agent-service` и ключ OpenAI ingress записаны
в `credentials.json` внутри `--home`. Файл приватный; не пересылайте его и не коммитьте.
Возьмите пароль admin в защищённом терминале/редакторе и выполните:

```bash
.venv/bin/python signed/0.1.6/scripts/smoke_http.py --url http://127.0.0.1:18000
```

Скрипт спросит пароль скрыто, проверит readiness, вход, зависимости и обычный `/chat`
запрос. Токены и текст ответа не печатаются. Запрос поступает в настроенную LLM и может
расходовать её квоту. Это первичная проверка, не полноценный нагрузочный или security-тест.

Для `/v1/chat/completions` нужны **оба** заголовка: `Authorization: Bearer <JWT>` и
`X-Uter-Ingress-Secret: <openai_ingress_key>`. Последний обычно добавляет доверенный
reverse proxy. Без него endpoint отвечает 403. `/auth/token` принимает form-urlencoded
`username` и `password`; `/chat` использует JWT.

Отдельный LLM judge по умолчанию отключён — это отдельная зависимость, а не основной
LLM API. Для его включения добавьте `prepare --judge-url http://HOST:11434 --judge-model MODEL`.
Требуется Ollama API, модель должна быть уже загружена; включается fail-closed.
Toxicity-модель, проверки ввода/вывода и аудит работают независимо от него.

## Автоматизация и секреты

| Этап | Что выполняется автоматически | Что остаётся оператору |
|---|---|---|
| Подготовка | `prepare` создаёт конфигурацию, ключи Uter и ресурсы для выбранного backend. | Выбрать среду, подготовить LiteLLM, имя модели, ключ, сеть и доверие к сертификатам. |
| Первая установка | `check` проверяет рендеринг; `install` скачивает образы, запускает компоненты и ожидает готовности. | Проверить доступ к registry и LLM, выполнить smoke и настроить TLS-доступ. `check` не проверяет соединения; smoke автоматически не выполняется. |
| Обновление | Контроллер проверяет подпись и совместимость, создаёт зашифрованную копию, обновляет компоненты и выполняет smoke. | Получить и проверить подписанные комплекты и ключ издателя; безопасно хранить и отдельно вынести копию и её ключ. |
| Восстановление | Создаются отдельные проект или namespace и тома; данные восстанавливаются, запускается smoke. | Проверить данные и внешние зависимости, выбрать момент и вручную переключить трафик. |

Интерактивный мастер объединяет перечисленные шаги установки и выполняет
авторизованный smoke после запуска. В ручном варианте отдельные команды и проверка
остаются за оператором. Пользовательские сеть, доверие, расписание резервных копий
и внешние системы всё равно требуют настройки.

Из проверенного комплекта доступна предварительная проверка с машины
оператора:

```bash
.venv/bin/python signed/0.1.6/scripts/preflight.py --backend compose --llm-url "$LLM_URL" \
  --llm-model "$LLM_MODEL" --llm-key-file "$LLM_KEY_FILE"
```

Для Kubernetes укажите `--backend kubernetes --context MY_CONTEXT`. Проверка отправляет реальный короткий
запрос и может расходовать квоту. Она не создаёт контейнеры или Pod и явно сообщает,
что сеть и доверие сертификатам внутри них, registry и CNI/CSI/RBAC не проверены.
Ранее выпущенный `0.1.4` эту команду не содержит.

Для Compose комплект также содержит `workload_preflight.py`: по явно
подтверждённой подписи он запускает проверку в одноразовой сети из локального образа
Guardrail и передаёт ключ только через stdin. Это проверка Python-клиента внутри образа,
а не самого Uter, будущей Compose-сети или Kubernetes; подробности и уборка после
прерывания описаны в [руководстве](docs/corporate-litellm-deployment.md).

В `0.1.6` установка и обновление Compose поддерживают `--offline` при предварительно
доставленных локальных образах с точными digest. Обновление требует локальных образов
обоих выпусков. [Проверка в изолированном CI](https://github.com/prince174/uter_deploy/actions/runs/40868904632)
подтвердила обновление `0.1.4 → 0.1.5` без доступа Docker daemon к registry и отказ
при отсутствии образа; использовалась тестовая LLM-заглушка. Новый переход на
`0.1.6` этим прогоном не проверялся.
Kubernetes offline не поддерживается; LLM остаётся внешней зависимостью. Для Kubernetes
есть отключённый по умолчанию [профиль ограничения исходящего трафика](docs/egress-networkpolicy.md),
который оператор настраивает под свой DNS и LiteLLM. [Проверка с Calico](https://github.com/prince174/uter_deploy/actions/runs/40866723144)
прошла для Pod-селекторов с опубликованными образами и тестовой LLM-заглушкой;
IPv4 ipBlock и другие CNI требуют отдельной проверки. mTLS, Ingress, DNS, ротация секретов и миграция внешних систем
настраиваются отдельно.
Наличие функций и примеры проверок не подтверждают работу в конкретном окружении.
Подробнее, включая закрытый контур и действия при сбое:
[инструкция для LiteLLM и vLLM](docs/corporate-litellm-deployment.md).
Команда одной зашифрованной копии для подключения к планировщику описана в
[инструкции по резервному копированию](docs/scheduled-backup.md); она не создаёт
расписание: его должен настроить оператор.

Для неинтерактивного prepare задайте `--llm-url`, `--llm-model`, `--llm-key-file`.
Файл ключа может быть пустым для LLM без авторизации. Секреты не передавайте в командной
строке. Вместо `--inputs` можно указать `--images`, `--policy`, `--profiles` отдельно.

В `--home` сохраняются `runtime/`, `credentials.json`, `install.json`, копии Compose/Helm
и `empty.env`; для Kubernetes дополнительно `resources.yaml`, `values.yaml`.
POSIX-права каталога — 0700, секретных файлов — 0600; install выставляет читаемые
контейнерами UID/GID для bind-mount. Не используйте `chmod -R 777`.
`resources.yaml` содержит секреты открытым текстом; Kubernetes Secret сам по себе
не является шифрованием. Резервируйте весь каталог зашифрованным способом.

Повторный prepare в существующий каталог запрещён, ключи не ротируются автоматически.
`git pull` не меняет копии шаблонов существующей установки. Уже существующие Compose
project или Kubernetes namespace не принимаются автоматически. На Windows поддержаны
подготовка/рендеринг с отдельно настроенными ACL; install выполняется на Linux.

## Ошибки, повторный запуск и обновление

При ошибке `install-state.json` остаётся `pending`. Повторный install блокируется;
ресурсы, данные и ключи сохраняются. Вывод команд скрывается, поскольку он может
содержать секреты. Диагностируйте занятость порта, доступ к registry/LLM, PVC и события
Pod. В Kubernetes: `kubectl --context MY_CONTEXT -n uter-instance get events` и
`describe pod POD`. До ручного продолжения подтвердите контекст и принадлежность
ресурсов вместе с администратором; имена и метки сами по себе этого не доказывают.
Не удаляйте каталог или volumes ради повтора.

Из проверенного комплекта можно получить ограниченную диагностику первой
установки, например:

```bash
.venv/bin/python signed/0.1.6/scripts/install_recovery.py --home /srv/uter-instance \
  --expected-backend compose --expected-name uter-instance --expected-context default
```

Для Kubernetes укажите `--expected-backend kubernetes` и использованный context.
Флаг `--inspect-runtime` дополнительно читает ограниченную часть метаданных Docker
или Kubernetes, не меняя ресурсы и не читая Secret. Существующие `pending` не содержат
идентификаторов, доказывающих владельца ресурсов: диагностика возвращает код 2 и
`inconclusive`, а не разрешение на автоматический повтор. Команда отсутствует в `0.1.4`.

Readiness не заменяет проверку поведения. До открытия доступа проверьте свои запросы,
политику блокировок, TLS и резервное копирование.

Установку `install.py` можно передать под управление `uterctl.py`: команда adoption
сверяет работающие образы, файлы развёртывания и подписанный комплект, затем выполняет
проверку сервиса. При обновлении контроллер создаёт зашифрованную резервную копию
перед заменой компонентов. Для этого нужны выпущенные подписанные комплекты и отдельно
полученный и проверенный доверенный ключ. Тестовые ключи
и версии из CI не предназначены для эксплуатации. Детали проверок и ограничений:
[реальная LLM и обновление](docs/real-llm-upgrade-validation.md).
Команды восстановления создают новую отдельную установку из проверенной копии;
переключение трафика и внешние зависимости остаются за оператором. См.
[обновление и восстановление](docs/managed-update-recovery.md).
`releases/example.json` не устанавливается.
Новый формат: `runtime/`, `RUNTIME_DIR`, `runtime.toml`, chart 0.2.0; старые каталоги
автоматически не переименовываются.

## Registry и CI

- `publish-images.yml`: проверка исходного CI run, SHA256 архивов и слоёв, публикация
  трёх образов GHCR, проверка выбранной видимости, обе установки.
- `verify-installation.yml`: проверяет установку из CI-артефакта.
- `verify-released-installation.yml`: повторяет проверку из архива GitHub Release
  и checkout его тега; job не имеет токена доступа к исходному проекту.
В опубликованном выпуске указан публичный GHCR; Docker Hub не используется.
Подготовка корпоративного Nexus и границы поддержки описаны в
[инструкции по Nexus](docs/nexus-registry.md). Результаты установки:
[отчёт проверки](docs/registry-installation.md).

CI использует только временные runner, namespace и volumes. Локальный Docker и
основной проект при разработке развёртывания не запускаются и не изменяются.
